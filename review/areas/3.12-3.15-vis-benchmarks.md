## What it does
**Visualization.** `pycauset.vis` builds three Plotly figures from a `CausalSet`: the embedding
(points at their coordinates, with an optional relation overlay), the Hasse diagram (links at
their coordinates) and the causal-matrix heatmap.
- Above `max_points` each plotter draws a seeded random subset of elements, with a
  `PyCausetPerformanceWarning`.
- The spacetime supplies its outline (`boundary()`) and its axis names (`display_axes()`).
- Plotly is optional. It is imported when `pycauset.vis` is imported, and that happens on the
  first `pc.plot_*` call or method call. Without Plotly the plotters raise a clear
  `ImportError` [repro].
- Coordinates come from `CausalSet.coordinates()`, which regenerates them from
  `(spacetime, seed)`.
- Links come from the engine's transitive reduction. No PyCauset result is computed by NumPy.
  NumPy only does figure-data plumbing (`np.ix_`, `np.triu`, `np.nonzero`, `np.argwhere`) on a
  dense export of `C` (C-2).

**Benchmarks, demos and tools.**
- 8 tracked benchmark scripts. CI runs `parity.py` report-only on 3 OSes (ci.yml:84-88) and
  lints `benchmarks/` with pyflakes.
- 5 demos, not run anywhere.
- Two PowerShell wrappers: `build.ps1` (a pip wrapper) and `release.ps1` (tags and pushes).
- `BENCHMARKS.md` at the root is the user-facing index and holds the numbers.
- `tests.atlas.timing` is the real per-operation timing. It imports PyCauset before NumPy.

What works [repro]:

## Findings

**C-1 (S2 major, silent wrong plot) A causet built from a matrix is plotted at invented
coordinates: lines join points that are not causally related there, and the picture changes
on every construction.** [repro, `vis1.py` c]
- Where: `vis.py:129, 269, 274` call `causet.coordinates()`, which regenerates points from
  `(spacetime, seed)` (`causet.py:349-357`). `CausalSet(n, matrix=M)` sets the spacetime to the
  default 2D diamond (`causet.py:118`) and the seed to `random.randint` (`:120-121`). Neither
  has anything to do with `M`.
- Repro: build a 30-element total order with
  `CausalSet(n=30, matrix=pc.causal_matrix(np.triu(ones, 1)))`.
  - 221 of its 435 related pairs are spacelike at the plotted coordinates.
  - `plot_hasse` draws its 29 chain links between those random points.
  - Two constructions from the same matrix give different coordinates
    (`np.allclose(...) == False`).
- Scenario: plot a causet built from data, from `pc.synthetic`, or from an edited matrix. The
  figure looks like a diamond sprinkling and gives no warning.
- Fix: a `CausalSet` made from a matrix has no embedding. `coordinates()` raises `ValueError`
  ("built from a matrix: no coordinates"). `plot_embedding` and `plot_hasse` raise too.
  Optionally, `plot_hasse` could later lay out by layers (`c.layers()`) instead.
  `plot_causal_matrix` keeps working.
- Regression test: `plot_embedding(CausalSet(n, matrix=M))` raises. A sprinkled causet saved
  and loaded still plots the same coordinates.

**C-2 (S2 major, out-of-core) Every subsampled plot first exports the whole causal matrix to
NumPy. The heatmap exports it as int64, so the cap that makes large sets plottable does not
protect memory.** [repro, `vis2.py`]
- Where:
  - `vis.py:390, 392`: `np.array(causet.C, dtype=int)`, then `[np.ix_(indices, indices)]`.
  - `:270`: a dense `bool` export, then `np.ix_` (Hasse subset).
  - `:150-153`: a dense `bool` export, then `np.triu` (a second copy), then `np.nonzero`
    (`show_relations`).
- Measured, n = 12,000:
  - `plot_causal_matrix` with the default 2,000-point cap: peak RSS 63 -> **1,301 MiB** for a
    2000 x 2000 image.
  - `plot_hasse` with a 500-point subset: 219 MiB.
  - `show_relations` with `max_points=2000`: 230 MiB.
- Extrapolated:
  - At n = 50,000 the heatmap needs n² x 9 B, about **22 GB**.
  - At demo 06's n = 100,000 it needs about 90 GB.
  - The export guard has no default ceiling (`export_guard._EXPORT_MAX_BYTES = None`), so
    nothing stops the export.
  - The causal matrix itself is 625 MB.
- Fix:
  - Select in the engine: `C[idx][:, idx]` works today and returns the right 2000 x 2000 bit
    matrix (`equal: True` against the NumPy route). `C[np.ix_(...)]` is not supported
    ("Advanced index array must be 1D").
  - Export only that, as `bool` (or `uint8` for imshow).
  - Drop `np.triu`.
  - With no subset (`n <= max_points`) the export is n² at n <= 2,000 / 50,000. Fine for the
    heatmap. `show_relations` on 50,000 points would still export 2.5 GB, so it needs its own
    cap or an engine nonzero.
- Regression test: under `set_export_max_bytes(4 * max_points**2)`, a subsampled
  `plot_causal_matrix` / `plot_hasse` / `show_relations` of an n = 3,000 causet succeeds. Today
  it raises because the full export exceeds the ceiling.

**C-3 (S3) `force=True` and `max_points=None`, the documented "render everything", raise above
100,000 elements.** [repro, `vis1.py` a]
- Where: `vis.py:129` calls `causet.coordinates(indices=None)` without `force`.
  `coordinates()` then raises `UserWarning` as an exception (`causet.py:349-353`). The same
  happens in `plot_hasse` (`:274`).
- Repro (the same `_n` trick `test_coordinates_safety` uses): `plot_embedding(c, force=True)`
  and `plot_embedding(c, max_points=None)` give
  `UserWarning: CausalSet has 200000 elements. Retrieving all coordinates is expensive...`.
  `max_points=150_000` works (a subset is passed as indices).
- Fix: pass `force=True` to `coordinates` when vis renders everything. Separately, the causet
  area should make `coordinates()` raise a real exception class (`ValueError`), not a
  `Warning`.
- Regression test: `plot_embedding(c, force=True)` with `c.n > 100_000` (a small sprinkle with
  `_n` patched and `_make_coordinates` mocked, or a real 100,001-element 2D sprinkle: 625 MB,
  too big for the suite, so mock).
