## What it does
`PersistentObject` is the base of every matrix and vector. It owns a `shared_ptr<MemoryMapper>`
(the storage, shared copy-on-write between views) and the view metadata. `ensure_unique` is
the write gate: it copies shared storage and bumps the storage version for the derived cache.
`MemoryMapper` gives out the bytes: `:memory:` storage comes from the C heap (calloc or malloc),
files are `mmap`ed / `MapViewOfFile`d behind a 64-byte header, and loaded snapshots are mapped
MAP_PRIVATE / FILE_MAP_COPY (F-093). `MemoryGovernor` is a leaked singleton. It tracks
RAM-backed objects in a list, answers `request_ram` / `can_fit_in_ram` from the OS's
available-RAM figure, and spills the oldest registered objects to `.tmp` files when a request
does not fit. `IOAccelerator` turns prefetch / discard calls into madvise /
PrefetchVirtualMemory. `StorageUtils` holds the memory threshold, the storage root and the
temp-file names. `SystemUtils` has one function: the home directory, used by the dormant GPU
hardware profile.

## Findings

**C-1 (S1 critical, silent data corruption) Two processes in one directory overwrite each other's
matrices.** [repro]
- Where: `src/core/StorageUtils.cpp:36,65-69` (names `prefix_<counter>.tmp`, counter starts at 0
  in every process) and `src/core/MemoryMapper.cpp:364-367` (`O_CREAT|O_TRUNC`, no `O_EXCL`).
  The import-time sweep in `python/pycauset/__init__.py:310` also deletes every `.tmp` in the
  root, including files another live process is using.
- Scenario: two scripts, notebooks or pytest-xdist workers in the same cwd (default root
  `./.pycauset`, F-017). Also `multiprocessing` with fork: the child inherits the counter and
  produces the same next names.
- Repro (`/tmp/pcr31/a.py`, `/tmp/pcr31/b.py`, threshold 1 KiB): process A creates a matrix full
  of 7.0 in `dense_float_0.tmp`. Process B starts, its import sweeps the root, and it creates a
  matrix full of 3.0, also named `dense_float_0.tmp`:
  ```
  A file dense_float_0.tmp a[0,0]= 7.0
  B file dense_float_0.tmp
  A after B allocated: a[0,0]= 3.0 sum 12288.0
  ```
  A's matrix silently holds B's data. If B's file is smaller, A gets SIGBUS instead.
- On Windows, `CREATE_ALWAYS` on a file another process has mapped fails, so the second process
  gets "Failed to open file" instead [citation].
- Fix:
  - Put a process-unique component in the name, created with `mkdtemp` or pid plus a random
    token: a per-process subdirectory `./.pycauset/<pid>-<rand>/`.
  - Open new files with `O_EXCL` / `CREATE_NEW` and fail loudly on a collision.
  - Make the import sweep remove only the directories of dead processes (check the pid, or hold
    an flock on a lock file in each subdirectory).
  - Reseed the counter or token in a `pthread_atfork` child handler.
- Regression test: two subprocesses, interleaved as above.

**C-2 (S1 critical, crash or wrong values under memory pressure) The governor frees storage that a
running kernel is reading.** [repro]
- Where: `MemoryGovernor::evict_until_fits` (`src/core/MemoryGovernor.cpp:307-345`) calls
  `victim->spill_to_disk()` (`src/core/PersistentObject.cpp:150-187`) on any registered RAM
  object, including operands of the operation that is allocating. `spill_to_disk` replaces
  `mapper_`, which frees the heap block when the storage is not shared. Every raw pointer
  obtained from `data()` before the allocation then dangles.
- Confirmed instance: `bit_popcount_matmul` (`src/compute/cpu/CpuMatmul.cpp:163-167`) takes
  `a.data()` and then allocates `b_transposed_mat`.
- Repro (`/tmp/pcr31/uaf.py`): bool `a` is 8 x 2^19 and `b` is 2^19 x 64, both in RAM. The
  margin is set so that the 2 KB result fits and the 4 MB transposed temporary does not:
  `G.set_safety_margin(avail - 1 MiB); c = a @ b`. Run with `MALLOC_MMAP_THRESHOLD_=131072`, so
  that free returns the pages to the OS:
  ```
  Fatal Python error: Segmentation fault ... line 15 in <module>   (c = a @ b)
  #0 dot_product_avx512  #1 bit_x_bit_kernel  #2 CpuSolver::matmul  #3 dispatch_matmul
  ```
  The margin only stands in for real memory pressure; under real pressure the same thing
  happens on its own. Without `munmap` the kernel reads freed heap: silent wrong values.
- Same class [citation]: `export_numpy` releases the GIL while it holds `b.data()`
  (`src/bindings/bind_matrix.cpp:237-244`), and `to_dense` runs without the GIL (229-230). Any
  other Python thread's allocation can spill the object being exported.
- Fix (design):
  - An object must not be spilled while an operation uses it. Options: an operation-scoped
    `InUse` guard (an atomic count on `PersistentObject` or the mapper) that the entry
    functions take for their operands and the result, and that `evict_until_fits` skips. Or
    spill only storage that no kernel can hold, i.e. call eviction only from allocation sites
    outside kernels.
  - Lock the victim's `mapper_` swap against readers on other threads.
- Regression test: the repro above (forced margin), plus an export from another thread.

**C-3 (S2 major, out-of-core) Temp files of dead objects stay on disk until the process exits.**
[repro]
- Where: `~PersistentObject` (`src/core/PersistentObject.cpp:52-62`) only unregisters. The file
  is deleted only in `close()` (71-92), which nothing calls during a session; the atexit hook
  calls it (`_internal/runtime.py:69-82`). `MemoryMapper::~MemoryMapper` unmaps but never
  unlinks.
- Repro (threshold 1 KiB): 5 iterations of `a = pc.matrix(np.ones((64,64))); b = a + a; del a, b`
  leave 10 files (`dense_float_0..9.tmp`) after `gc.collect()`.
- Scenario: a loop over file-backed (≥ 1 GiB) results, spills and cow copies fills the disk, which
  is exactly the out-of-core case.
- Fix: the storage owns the file. `MemoryMapper` gets an `unlink_on_close` flag, set for
  auto-named temp files (create, spill, cow copy), and its destructor unlinks after unmapping. On
  POSIX it can unlink right after `mmap`, so a crash leaves nothing behind either. On Windows,
  `FILE_FLAG_DELETE_ON_CLOSE` or `FILE_DISPOSITION_DELETE`. Then `close()` and
  `is_temporary_`'s file role go away.
- Docs: `Memory and Data.md` "On destruction it unmaps, and if the backing was a temporary file,
  deletes it" is false today.

**C-4 (S2 major, out-of-core) Each file-backed object holds an open fd; ~1,020 live objects
exhaust the default limit.** [repro]
- Where: `src/core/MemoryMapper.cpp:367` opens the file, and it stays open until `close_file`
  (548). The fd is opened without `O_CLOEXEC`, so it also leaks into subprocesses.
- Repro (`ulimit -n 1024`, threshold 0): 1100 × `pc.zeros((4,4))` fails at object 1021 with

- Scenario: block matrices with many file-backed leaves, or a causal set analysis that keeps many

- Fix: on POSIX, close the fd right after `mmap`. The mapping keeps the file alive. Reopen by

**C-5 (S2 major) On POSIX every msync and madvise of file-backed storage fails with EINVAL: flush,
prefetch and discard do nothing.** [repro]
- Where: `mapped_ptr_ = base_ptr_ + adjustment`, where adjustment = 64 (the header), at
  `src/core/MemoryMapper.cpp:383,523`. `flush()` calls `msync(mapped_ptr_, ...)` (565, 581), and
  `IOAccelerator` calls `madvise(base + offset, ...)` (`src/core/IOAccelerator.cpp:245,252,259,266`).
  Both need a page-aligned address. Every return value is ignored.
- Repro (strace of `get_accelerator().prefetch/discard` and `copy_storage` on a 512² file-backed
  matrix):
  ```
  madvise(0x7f8663200040, 2097152, MADV_WILLNEED) = -1 EINVAL
  madvise(0x7f8663200040, 2097152, MADV_HUGEPAGE) = -1 EINVAL
  madvise(0x7f8663200040, 2097152, MADV_DONTNEED) = -1 EINVAL
  msync(0x7f8663200040, 2097152, MS_SYNC) = -1 EINVAL      (source flush in copy_storage)
  msync(0x7f8660e00040, 2097152, MS_SYNC) = -1 EINVAL      (dest flush: pc.save's payload)
  ```
- Impact:
  - `pc.save` and spills are not durable on a crash. The Storage guide (line 320) promises they
    are.
  - The block-matrix prefetch and discard hints are no-ops.
  - If fixed naively, the `MADV_HUGEPAGE` would come back (see the IOAccelerator notes).
- Fix: round the address down to the page and extend the length (one helper, used by flush and
  madvise). Check the return values and raise on msync failure. Drop the MADV_HUGEPAGE.
- Test: assert the syscall result through a test hook, or via `mincore` after a prefetch.

**C-6 (S2 major) Spilling a view duplicates shared storage and counts memory as freed that stays
allocated.** [repro]
- Where: every view of `:memory:` storage registers the full storage size
  (`src/core/PersistentObject.cpp:44-46`). The governor spills each one separately
  (`MemoryGovernor.cpp:333-334` adds `victim_size` to `freed_so_far`). `spill_to_disk` copies the
  shared bytes into a new file for that one view, and the RAM stays alive while another view
  holds it.
- Repro: a 2 MiB matrix plus 9 views (`a.T`, `a * 2.0`), then one allocation under pressure. This
  writes 10 spill files, 20 MiB on disk, for one 2 MiB storage, and the views no longer share
  storage. With a moderate shortfall, spilling only `a` reports 2 MiB freed while 0 bytes were
  freed, so `request_ram` returns true and over-commits.
- Fix:
  - Track storages, not objects: register the `MemoryMapper` once and keep the LRU on mappers.
  - Spill a storage by swapping the bytes under the mapper. All views keep the same
    `shared_ptr` and see the file. This needs the mapper to support re-backing: a pointer swap
    under the C-2 guard.
  - Count only storage that is actually released.

**C-7 (S3) The "LRU" is creation order: nothing ever calls `touch()`.** [repro by grep]
- Where: `PersistentObject::touch` (`src/core/PersistentObject.cpp:144`) and
  `MemoryGovernor::touch` (`src/core/MemoryGovernor.cpp:272`) have no callers in `src/`,
  `include/` or `python/`. The governor therefore spills the oldest object, even one used in every
  iteration of a loop, before a temporary created a moment ago. Architecture.md ("spills the least
  recently used") and Memory and Data.md ("Touching an object moves it to the front") describe a
  policy that does not run.
- Fix: touch operands in the operation entry functions (one place, next to the C-2 guard), or
  call it FIFO in the docs.

**C-8 (S3) `map_region` leaks every mapping on POSIX; `fill_random` of a file-backed causal matrix
leaks a 64 MB mapping per chunk.** [repro]
- Where: `MemoryMapper::unmap_region` is empty on POSIX (`src/core/MemoryMapper.cpp:693-703`).
  It is called from `TriangularMatrix<bool>::fill_random` (`src/matrix/TriangularBitMatrix.cpp:260,290,309,337,368`).
- Repro: threshold 1 KiB, `TriangularMatrix.random(20000)` three times, deleting each result.

- Fix: drop the region API. `fill_random` can write through the normal full mapping (MAP_SHARED

**C-9 (S2 on Windows, suspected) `unmap` / `map_all` are wrong on Windows: `fill_random` of a
file-backed causal matrix throws and leaves a null data pointer.** [citation]
- Where:
  - `unmap` calls `UnmapViewOfFile(mapped_ptr_)` (`src/core/MemoryMapper.cpp:596-598`).
    `mapped_ptr_` is base + 64, not the view's base address, so the call fails (unchecked) and
    the view stays mapped, while `mapped_ptr_` is set to null.
  - `map_all` calls `MapViewOfFile(hMapping_, ..., offset_ = 64, data_size_)` (629-632). 64 is
    not a multiple of the 64 KiB allocation granularity, so it fails with
    ERROR_MAPPED_ALIGNMENT and throws "Failed to map view of file". It also never updates
    `base_ptr_`.
- Scenario: `pc.TriangularMatrix.random(n)` above the memory threshold (or `storage="disk"`) on
  Windows. Not run (no Windows here). Same fix as C-8.

**C-10 (S3 performance, out-of-core) Every new file is truncated, fallocated and fully pre-faulted
(`MAP_POPULATE`).** [repro of the syscalls; impact suspected]
- Where: `src/core/MemoryMapper.cpp:387` (ftruncate), 443 (fallocate mode 0 to the same size),
  508 (`MAP_POPULATE`). strace of one file-backed `pc.zeros((1000,1000))`:
  `ftruncate(3, 8000064)`, `fallocate(3, 0, 0, 8000064)`,
  `mmap(..., MAP_SHARED|MAP_POPULATE, 3, 0)`.
- Impact: file-backed objects are by definition ≥ the threshold (1 GiB). MAP_POPULATE faults the
  whole file into the page cache at creation. For a result larger than RAM that is O(size) work
  and evicts the operands before the first tile is computed, which is the opposite of what the
  streaming manager needs. The Windows `prefetch(0, final_size)` on create
  (`PersistentObject.cpp:227-234`) does the same.
- Fix: no populate for file-backed storage, or only below a small size. Keep one of ftruncate or
  fallocate (fallocate for early ENOSPC, ftruncate as its fallback).

- Where: `src/core/MemoryGovernor.cpp:97-129` reads only `/proc/meminfo` MemTotal and
  MemAvailable, which report the host, not the container.
- Scenario: under a docker `--memory`, Kubernetes or Slurm cgroup limit (the usual way physicists
  run long causal-set jobs), the governor thinks the host's RAM is free and never spills, and the
  job is OOM-killed.
- Not reproducible here (no cgroup limit in this container).
- Fix: also read `/sys/fs/cgroup/memory.max` minus `memory.current` (v2), or
  `memory.limit_in_bytes` (v1), and take the minimum.

**C-12 (S3 out-of-core, suspected) Loaded snapshots are mapped copy-on-write for the whole view.**
[citation]
- Windows: `MapViewOfFile(FILE_MAP_COPY)` (`src/core/MemoryMapper.cpp:282,298`) charges the
  entire view to the commit limit at map time (MSDN, MapViewOfFile: "the system and process
  commit charge taken is for the entire view"). `pc.load` of a snapshot larger than RAM +
  pagefile would fail with "Failed to map view of file".
- POSIX: every page written to a loaded snapshot becomes anonymous memory. The governor neither
  sees nor spills it, so overwriting a big loaded matrix (`fill`, slice assignment) grows RSS up
  to OOM.
- Fix: a read-only mapping (`PAGE_READONLY` / `PROT_READ`) for snapshots. The first write goes
  through `ensure_unique` into a real copy, which `ensure_own_mapping` already does; that copy
  goes to RAM or a temp file by the threshold. The F-093 guarantee stays, enforced by a fault
  instead of by private pages.

**C-13 (S4) Writing to a small loaded matrix whose storage is shared copies it into a file, not
RAM, and the file is not temporary.** [repro]
- Where: `copy_storage_now` (`src/core/PersistentObject.cpp:112-124`) uses RAM only if the source
  was RAM.
- Repro: `m = pc.load('a.pycauset')` (4×4); `v = m.T`; `m[0,0] = 5` gives backing
  `cow_copy_0.tmp`, `is_temporary == False`.
- Fix: decide the copy's placement like a new allocation (threshold, then `request_ram`), and
  mark auto-named files temporary (or C-3).

**C-14 (S4, UB) `memcpy` from null for empty storage in `copy_storage_now` and `spill_to_disk`.**
[citation]
- Where: `src/core/PersistentObject.cpp:127,166` and `src/matrix/MatrixBase.cpp:88`. F-025 fixed
  only `copy_storage` (282).
- Scenario: an empty matrix that shares storage (`e = pc.zeros((0,0)); f = e.T`) being written,
  or spilled. UBSan (`asan.yml`, `-fno-sanitize-recover`) would abort.
- Fix: `if (size)` guard, or one `copy_bytes` helper used by all three.

**C-15 (S4, latent) Derived-cache race: a value computed before a write can survive the write.**
[citation]
- Where: `include/pycauset/core/MemoryMapper.hpp:63-70` versus 84-89. `bump_version` increments
  outside the lock and clears only when `has_cache_` is already true. A `cache_put` that passed
  its version check (inside the lock) but has not yet stored the entry and set `has_cache_` is
  missed: the stale entry stays after the bump.
- Scenario: needs a write and a cached computation on the same storage from two threads.
  Unreachable from Python today (the GIL is held in both), so reachable only once ops release
  the GIL.
- Fix: store `computed_at` with the entry and have `cache_get` return it only if it equals
  `version()`. That needs no lock in `bump_version`, and the clear becomes an optimisation.

**C-16 (S4, suspected) `get_accelerator()` hands Python a raw pointer that is freed on the next
storage swap.** [citation]
- Where: `src/bindings/bind_matrix.cpp:351-354` (`reference_internal` ties the matrix's lifetime,
  not the accelerator's); the accelerator is reset at `src/core/PersistentObject.cpp:134,171,225`.
- Scenario: `acc = m.get_accelerator(); v = m.T; m[0,0] = 1; acc.prefetch(0, n)` is a
  use-after-free. Spills do the same.
- Fix: remove `get_accelerator` from the binding. Python's `_io_hint` can call a
  `prefetch(offset, size)` / `discard` method on the matrix, which resolves the accelerator per
  call. Or make the accelerator stateless (a free function on the mapper).

**C-17 (S4 docs) The storage docs describe a different implementation.** [citation]
- `documentation/internals/Memory and Data.md`:
  - "RAM: VirtualAlloc on Windows, mmap with a shared-memory fd on macOS/Linux". It is the C heap
    (calloc/malloc) on all platforms (F-057, F-096).
  - "On destruction it unmaps, and if the backing was a temporary file, deletes it". False (C-3).
  - "keeps every PersistentObject in an LRU list. Touching an object moves it to the front". It
    keeps RAM objects only, nothing touches, and the back is the most recent (C-7).
  - The `use_ram_buffer()` / `use_disk_file()` snippet names functions that do not exist and
    omits the threshold.
  - "madvise / MAP_POPULATE pulls pages in", "Discard: MADV_DONTNEED": no-ops (C-5).
  - "Solvers declare their access pattern up front ... the accelerator turns that into the right
    prefetch/discard syscalls". No solver issues a hint; `Reverse`, `Random` and `Once` are
    ignored.
- `documentation/guides/Storage and Memory.md:320`: "Explicit flushes ... msync (Linux) ensure
  data reaches physical media" is false (C-5). Line 137 ("if something is spill-backed and large,
  you must opt-in") should be checked against F-016 (guard by size only).
- `documentation/docs/classes/core/pycauset.MemoryHint.md`: "The solver emits a hint" (none does).
  "sequential / strided (bool) convenience flags" are not bound; they are static constructors.
- `documentation/internals/Architecture.md` Storage: "spills the least recently used": it spills
  the oldest (C-7). It should also say that two processes must not share a backing dir until C-1
  is fixed.

## Proposed changes (cleanup / Phase 4)

1. **Storage ownership (C-1, C-3, C-4, C-6, C-13):**
   - `MemoryMapper` owns its file. It gets a process-unique name (created with `O_EXCL` in a
     per-process directory), is unlinked when the mapper dies, and keeps no fd after mapping on
     POSIX.
   - The governor tracks mappers (storages), not `PersistentObject*`. A spill re-backs the mapper
     in place, so all views keep sharing.
   - Placement of copies goes through the same decision as new allocations.
   - With this, `close()`, `is_temporary_` / `set_temporary` (as a file-lifetime flag), the Python
     temp-file bookkeeping (`mark_temporary_if_auto`, `_live_matrices`, the atexit `close()`
     sweep) and most of `_storage.py` can go.
2. **Spill safety (C-2):** an operation-scoped in-use guard on operand and result storages, taken
   once in the entry function (with `touch`, C-7). The governor skips guarded storages.
   Document that the governor never spills inside a kernel.
3. **One aligned-range helper** for msync / madvise / unmap (C-5), used by flush, IOAccelerator
   and close, with return values checked.
4. **Remove the region API** (`map_all`, `unmap`, `map_region`, `unmap_region`) and rewrite
   `TriangularMatrix<bool>::fill_random` on the plain mapping (C-8, C-9). Remove
   `pin_region`/`unpin_region` with the CUDA move.
5. **Snapshots read-only + explicit CoW (C-12)** instead of MAP_PRIVATE / FILE_MAP_COPY.
6. **No MAP_POPULATE / create-time prefetch** for file-backed storage; keep one of ftruncate or
   fallocate (C-10).
7. **cgroup-aware available RAM** (C-11).
8. **Dead code to delete:**
   - Windows `VirtualAlloc` / `VirtualFree` branches (`MemoryMapper.cpp:269-277,326-328`)
   - `MatrixBase::spill_to_disk(filename)`
   - `copy_storage`'s filesystem branch
   - `StorageState::TRANSITIONING`
   - `MemoryGovernor::update_size`, `get_max_pinned_memory`, `clear_/has_pinning_budget_override`
     (or move them with CUDA)
   - `IOAccelerator::process_hint`'s guessed Strided semantics (keep Sequential, or implement
     the patterns the enum declares)
   - `IOAccelerator`'s MADV_HUGEPAGE
   - unused includes (`<iostream>` in MemoryGovernor and IOAccelerator, `<future>`, SystemUtils'
     platform headers, PersistentObject's SystemUtils, fstream and algorithm)
   - the archaeology comments listed above
9. **SystemUtils:** fold `get_home_directory` into AutoSolver (its only user, GPU) and delete the
   class.
10. **Tests to add:**
