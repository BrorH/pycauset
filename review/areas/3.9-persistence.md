## What it does
`pc.save(obj, path)` (`persistence.save`):
1. A CausalSet is saved as its causal matrix plus `object_type`, `n`, `spacetime`, `seed`.
2. Closures and windows are written out first (`_materialize_for_save`); other views keep the
   storage and record `is_transposed`, `is_conjugated`, `scalar`.
3. `copy_storage(<stem>.raw_tmp)` has the engine memcpy the storage into a new mapped file (with
   a 64-byte raw header) and msync it.
4. Python then streams that file in 1 MiB chunks into `<name>.part` after a zeroed 4096-byte
   header, appends a CRC'd metadata block (typed map: rows, cols, structure, dtype,
   has_diagonal, view, seed, payload_uuid, payload_layout, derived), writes the preamble and
   two slots (generation 1 and 0, same pointers), and `os.replace`s `.part` over `path`.
5. `.raw_tmp` is deleted.

`pc.load` reads the header and picks the active slot. It checks the metadata block's framing and
CRC, then `_open_storage` maps the payload at offset 4096, MAP_PRIVATE (F-093). It re-applies
transpose and conjugation, and imports the `derived` entries into the new storage's cache.

Block matrices go to a manifest container plus a `<name>.blocks/` directory of child containers,
with each child's `payload_uuid` pinned in the manifest. The export guard limits NumPy exports
by size; the engine has its own copy of the guard for native objects.

What works [repro]:
- Values. All 1,174 structure x dtype x view cells (13 structures, 15 dtypes, 15 views, including
  conj, H, conj_cscale, windows, rect_T, lazy_sum and closures) round-trip with identical NumPy
  values and dtype. This holds for RAM storage and for file storage (threshold 1 KiB)
  (`sweep.py`). Class, structure, dtype and view flags are kept, except where the object was
  written out first (windows, closures), by design.
- Derived values. In 934 matrix cells, sum, trace, det and norm served from the file's entries
  (2,603 hits) equal a fresh computation in every cell (`dsweep.py`).
- Overwriting. Saving over a loaded file leaves the loaded object reading the old values.
  Saving a loaded and edited object to its own path works. Saving the same path twice works.
- SIGKILL during a 488 MiB save leaves the old file loadable.
- Damaged headers. Truncation at 0, 8, 15, 100, 4095 bytes, mid-payload or mid-metadata, a bad
  version, a bad slot CRC, a bad metadata magic or CRC, an unknown structure or an unknown dtype:
  each raises a `ValueError` or `RuntimeError` that names the failed check.
- Empty matrices, 0 x 3 matrices, identity matrices and zero-length vectors round-trip.
- A CausalSet round-trips, coordinates included.

## File-by-file notes

### python/pycauset/_internal/persistence.py
1. Purpose: right place. Two writers of the same header and metadata block, `save`
   (505-549) and `_save_blockmatrix` (852-895), are copy-pasted.
2. Liveness:

     `is_transposed`.
   - The `hasattr(obj, "set_transposed")` / `hasattr(obj, "set_conjugated")` guards (621-625)
     are always true. If one were false the flag would be dropped silently, which goes against
     F-101's "now raises".

     re-check (371-372).
   - `payload_layout` is written (447, 468) and never read: the loader derives the layout from
     `structure`.
   - Slot B always gets generation 0 with the same pointers as A, so it is only a CRC backup.
     `hot_offset` / `hot_length` are always 0.
   - `seed` and `payload_uuid` are written for every object, but `payload_uuid` is used only for
     block pins. Load still raises without it (598-600).
3. Correctness:
   - The temp names are derived from the target path, so concurrent saves collide (C-1).
   - The derived entries are exported after the payload copy, a race (C-8).
   - The CausalSet spacetime is hard-coded to `"MinkowskiDiamond"` (461). That is the only
     spacetime today, but a second one would be saved silently as a diamond.
   - `_load_blockmatrix` checks child names and pins. Good.
   - The loader does not compare `payload_length` with what the shape needs (C-7).
4. Out-of-core:
   - Two full copies per save, plus a populated mapping (C-2).
   - Python reads the copy in 1 MiB chunks, so there is no full copy in Python memory. Good.
   - `_materialize_view_block` copies element by element in Python (C-5).
5. Errors:
   - Load errors are specific (see above). `"invalid slot length"` for a file truncated inside
     the slots could say "truncated header".
   - Concurrent saves to the same path give a bare `FileNotFoundError` on `.part` (C-1).
   - The `try/except OSError: pass` blocks in `_save_blockmatrix` (691-702, 716-726, 764-768,
     813-814) and `_replace_dir`'s "last resort non-atomic move" are silent fallbacks (C-10).
6. Concurrency: C-1, C-8.
7. Performance: `pc.save` of 488 MiB takes 1.2-1.5 s; `np.save` takes 0.14-0.17 s (C-2).
8. Duplication: the two writers above; the derived-entry codec lives in C++, the container codec

## Findings

**C-1 (S2 major, silent data corruption) Concurrent saves share temp names: one file gets the
other's payload under its own metadata.** [repro]
- Where: `persistence.py:396` `temp_raw = path.with_suffix(".raw_tmp")` and `:486`
  `part = path.with_name(path.name + ".part")`. The names are fixed, not unique: `r.pycauset` and
  `r.bak` share `r.raw_tmp`, and two saves of one path share `.part`. The `finally` (552-560)
  then deletes the other save's files.
- Repro (`c2.py`): two threads save a 3000² matrix of 1.0 to `r.pycauset` and one of 2.0 to
  `r.bak`. In 4 of 5 runs `r.pycauset` loads as all 2.0, or `r.bak` as all 1.0, with no error.
  Saving one path from two threads raises
  `FileNotFoundError: ... r.pycauset.part -> r.pycauset` in 4 of 5 runs.
- Also: `pc.save(m, "x.raw_tmp")` returns normally and leaves no file. `temp_raw == path`, and the
  `finally` unlinks the saved container (`c1.py`).
- Scenario: two worker processes or threads writing `result.pycauset` and `result.npz`, or a
  checkpoint thread and the main thread saving the same file.
- Fix: use unique staging names (`tempfile.mkstemp(dir=path.parent, prefix=path.name + ".")`), or
  drop `.raw_tmp` entirely (C-2). Never unlink a path that this call did not create.

**C-2 (S2 major, out-of-core and durability) A save writes the payload twice, syncs the copy it
deletes, never fsyncs the container, and leaves full-size leftovers after a crash.** [repro]
- Where:
  - `persistence.py:408`: `copy_storage` maps and populates a new file, memcpys the whole
    storage and msyncs it (`PersistentObject.cpp:123-137`).
  - `:487-497`: Python copies that file again into `.part`.
  - `:550`: `os.replace` with no `fsync` of `.part` or of the directory.
- strace of a 2 MiB save (`s1.py`): `msync` on `s1.raw_tmp` only, then `rename(.part, target)`,
  then `unlink(s1.raw_tmp)`. The container is never fsynced.
- Impact:
  - Disk peak is 2x the payload plus the old file: a 100 GB matrix needs 200 GB free.
  - The populated copy mapping adds the payload to RSS: maxrss went 1,024 -> 1,505 MiB for a
    488 MiB save.
  - 488 MiB takes 1.2-1.5 s against 0.14-0.17 s for `np.save` (`t1.py`).
  - After a power loss, the renamed file can be empty or partly written on filesystems without
    ext4's rename heuristic. F-122 says "`pc.save` ... synced"; the container is not.
  - SIGKILL during a save left `big.raw_tmp` (488 MiB) next to the target (`c3.py`). The import
    sweep only walks the backing directory, so it is never removed. The Storage guide says
    `.raw_tmp` lives in the backing directory and is "renamed/committed"; it is neither.
- Fix: write the container in one pass. Create `.part` (unique name, C-1) with the header
  reserved, have the engine copy the storage straight into it at offset 4096 (a
  `copy_storage_to(path, offset)` binding over `MemoryMapper(path, size, 4096, create_new)`, no
  populate), append the metadata, write the slots, `fsync(part)`, rename, `fsync(dir)`. On error,
  unlink only `.part`.

**C-3 (S2 major, stale results) Derived values loaded from a file are trusted without any check
against the payload or the engine that computed them.** [repro, version part citation]
- Where: `persistence.py:627-629` and `bind_core.cpp:173-201` import every entry at the current
  storage version. The metadata has no payload checksum and no engine or key-schema version
  (`meta` keys: `cols, derived, dtype, payload_layout, payload_uuid, rows, seed, structure, view`).
- Repro (`c5.py`): save a 6x6 matrix with det and sum cached. Edit `[0,0]` in place with
  `np.memmap(p, mode="r+", offset=4096)`, the usual out-of-core way to patch a file, then load:
  ```
  x[0,0] = 1000.0  det(x) = 55115.94  sum(x) = 37.998      (from the file)
  recomputed:      det(x) = 8335374.45  sum(x) = 1031.65   (NumPy det 8335374.45)
  ```
- Version skew: an entry computed by an older build is served forever after an upgrade that
  fixes that kernel. The review fixed many such kernels (F-059, F-094, F-113, ...). This breaks
  DERIVED_CACHE invariant 1 ("equals what recomputation would return now").
- The Container doc mentions that external payload changes go undetected (line 118-119); the
  user guide ("a determinant that took an hour is there again") does not.
- Fix:
  - Stamp the derived map with `engine` (the pycauset version) and `key_schema`, and drop every
    entry on a mismatch.
  - Store a payload checksum, computed in the save copy loop (free there, C-2). Verify it on the
    first hit of a loaded entry; that is O(n²) against the O(n³) it saves. Drop entries that are
    O(n²) to recompute (sum, trace, norms) from the file, because checking costs as much as
    recomputing.
  - Give `ReductionValue::Kind` explicit values.

**C-4 (S2 major, silent stale data) ThunkBlock caches results in Python and never notices a write
to a native leaf; block saves then store the stale values.** [repro]
- Where: `thunks.py:12-16` `_get_version` reads `obj.version`, which native matrices do not have,
  so no pins are taken. `materialize` (91-101) then returns `_cache` forever. This is result
  caching outside DerivedCache, which CLAUDE.md forbids.
- Repro (`c12.py`, `c13.py`): `out = block_matmul(BM([[a]]), BM([[a]]))`; evaluate; `a[0,0] = 7`.
  The block still reads 2.0 (fresh: 10001.0). After `pc.save(out, p)` the file holds 10001.0
  where `a @ a` is now 50.0. `save.md` says "Saving raises deterministically if any captured
  input is stale". It only does for `BlockMatrix.set_block`, which is the case
  `test_blockmatrix_save_raises_on_stale_thunks` checks.
- Scenario: `pc.matrix(((A, A), (A, A))) @ X`, then edit `A`, then use or save the product.
- Fix: pin `native._storage_version(leaf)` for MatrixBase / VectorBase (the binding exists). Better,
  drop the Python cache and recompute, or move it to DerivedCache when D.4 lands. Add a test
  that writes a leaf.

**C-5 (S3) Block-matrix persistence: view blocks change dtype and are copied element by element;
an interrupted overwrite loses the old snapshot.**
- `_materialize_view_block` (`persistence.py:661-682`) loops `get(i, j)` in Python into a NumPy
  array whose dtype comes from a hint table. [repro, `c6.py`]
  - A `complex_float16` SubmatrixView block loads back as `complex_float32`.
  - A 600x600 view block takes 0.19 s against 0.008 s for a plain block, so 10k² would take
    about a minute.
  - Fix: build the engine window `src[r0:r0+h, c0:c0+w]` and save it (`_materialize_for_save`
    writes windows out natively).
- Crash window [citation]: children are committed into the live `.blocks/` directory, and stale
  children are deleted (784-814), before the parent container is replaced (897). A crash in
  between leaves the old parent pointing at new or deleted children. Load then fails
  ("payload_uuid mismatch" / missing file): detected, but the old snapshot is gone.
  - Fix: write the new tree to `<name>.blocks.<token>/`, record that directory name in the
    manifest, replace the parent, then delete the old tree.

**C-6 (S3) Export-guard gaps.** [repro, `bm.py`, `c7.py`, `c8.py`, `c9.py`]
- `dtype=` is not counted. With `set_export_max_bytes(1000)`, `to_numpy(bool 30x30,
  dtype="complex128")` passes the 900-byte check and returns 14,400 bytes
  (`export_guard.py:155-156`). Fix: estimate with the target itemsize.
- BlockMatrix (code as of 02:59 UTC): `dtype` is `"mixed"`, so `ensure_export_allowed` finds no
  estimate and passes. Each leaf then goes through the native guard with `allow_huge=False`.
  Result: with a ceiling of 40 bytes, a 128-byte block matrix of 32-byte leaves exports, and
  `to_numpy(B, allow_huge=True)` still raises on a leaf. Fix: sum the leaf estimates; pass
  `allow_huge` down.
- `np.asarray(SubmatrixView)`, `to_numpy(SubmatrixView)` and the same for a ThunkBlock return a
  0-d object array, silently. The `export_to_numpy` docstring says they "export through their own
  `__array__`", but they have none. Fix: give them an `__array__` (or route them through their
  source's window), or raise `TypeError`.
- `to_numpy(M, copy=False)` silently returns a writable copy, and with `dtype=` it raises NumPy's
  "Unable to avoid copy". `np.asarray(M, copy=False)` raises `ValueError`. `to_numpy.md` promises
  a read-only view or a `UserWarning`. Fix: one rule. Raise as `__array__` does, and document it.

**C-7 (S3) The loader does not check that the payload is as long as the shape needs.** [repro, `c4.py`]
- Where: `_slot_valid` (`persistence.py:308-319`) only checks that `payload_offset +
  payload_length <= file_size`. The mapper maps `rows x cols` bytes from offset 4096 and checks
  only the file size, metadata included.
- Repro: an 8x8 float64 file whose metadata (valid CRC, newer slot) says 9x9 loads as a 9x9
  matrix. Its last 136 bytes are the metadata block read as values. With the dtype rewritten to
  int64 it loads reinterpreted, which is expected: the file says so.
- Scenario: a writer bug or a hand-edited file, today; a future layout change.
- Fix: the engine reports the storage byte size for (structure, dtype, rows, cols,
  has_diagonal); load requires `payload_length == expected`. Then drop or check `payload_layout`.

**C-8 (S3, concurrency) Payload and derived entries are captured at different times.** [citation]
- Where: `copy_storage` runs at `persistence.py:408`; `_derived_cache_export` runs at `:454`.
  Another Python thread can run in between (the GIL switches between bytecodes). If it writes the
  matrix and then computes `det`, the file gets the old payload and the new det.
- Fix: read the storage version and export the entries first, copy the payload, then re-read the
  version and drop the entries if it moved. Or do all three in one C++ call.

**C-10 (S3 on Windows, suspected; project-rule violation everywhere) Saving over a loaded file on
Windows, and silent fallbacks in block saves.** [citation]
- `MemoryMapper` opens snapshots with `FILE_SHARE_READ | FILE_SHARE_WRITE` and no
  `FILE_SHARE_DELETE` (`MemoryMapper.cpp:133`). `os.replace(part, path)` over a loaded file
  therefore fails with PermissionError on Windows, so the documented "an object loaded from the
  target keeps reading the old file" holds on POSIX only.
  - Fix: open with `FILE_SHARE_DELETE` (rename over a mapped file is then allowed on NTFS), or
    document it.
- `_replace_dir` (`persistence.py:704-729`): if the rename fails it does `rmtree(dst)` and then a
  non-atomic `shutil.move`, and errors are swallowed throughout `_save_blockmatrix`. This is
  exactly the "no silent fallbacks" case. Fix: let the OSError propagate.

## Proposed changes
1. **One-pass, unique, durable save (C-1, C-2):** unique `.part` from `mkstemp` in the target
   directory; the engine copies the storage into it at offset 4096 (no `.raw_tmp`, no populate);
   then metadata and slots, `fsync(part)`, rename, `fsync(dir)`. Unlink only what this call
   created. Correct the `.raw_tmp` docs and F-122's claim.
2. **Derived entries (C-3, C-8):**
   - stamp `engine` + `key_schema`
   - a payload checksum computed during the copy and checked on the first hit
   - persist only quantities that cost more than O(n²) to recompute
   - capture the version before the copy and check it after
   - explicit `ReductionValue::Kind` values
3. **ThunkBlock (C-4):** pin `_storage_version` of native leaves, or remove the Python cache.
4. **Load validation (C-7):** `payload_length == engine-computed storage bytes`; check or drop
   `payload_layout`.
5. **Block persistence (C-5, C-10):**
   - view blocks through the engine window
   - a new sidecar directory per save, named in the manifest, so a crash keeps the old snapshot
   - no silent rmtree / move fallbacks
   - `FILE_SHARE_DELETE` on Windows
6. **Export guard (C-6):**
   - target-dtype estimate
   - BlockMatrix: sum of the leaves, pass `allow_huge` down
   - SubmatrixView and ThunkBlock: export properly or raise
   - one `copy=False` rule
   - one size table (expose the engine's itemsize to Python)
7. **NumPy helpers (C-12):** `mmap_mode="r"` on load; atomic `save_npy` / `save_npz` (temp file
   and rename); an exact `load_npz` default key (first stored, or require a key when there are
   several).
8. **Docs (C-9):** rewrite Container Format and Storage Semantics to the format as written (key
   list, identical slots, no append path), update DERIVED_CACHE.md D.3, fix Storage and Memory
   71/99/118-124, `load.md` (CausalSet), the `to_numpy` / `set_export_max_bytes` docstrings and
   `to_numpy.md`.
