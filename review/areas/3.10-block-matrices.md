## What it does
`pc.matrix(grid)` with every element an engine matrix (or a block / view / thunk) builds a
`BlockMatrix`: a rectangular grid of leaves with row and column partitions. `pc.matmul`, `@`, `+`,
`-`, `*`, `/` with a `BlockMatrix` operand wrap the other operand as a 1x1 grid, refine both grids to
the union of the boundaries (`refine_partitions` cuts leaves into Python `SubmatrixView` tiles), and
return a new `BlockMatrix` whose leaves are `ThunkBlock`s. A thunk computes its tile on first access
(`get`, `np.asarray`, `pc.save`) through the leaf operators (`_leaf_matmul`: `pc.matmul` for engine
operands; `_leaf_elementwise`: the Python operators), caches the result, and raises
`StaleThunkError` when a pinned input's version changed. `DensePythonMatrix` is a list-of-lists
fallback that `SubmatrixView.__add__` / `__matmul__` produce. Saving writes a manifest container plus
`<name>.blocks/` with one child container per leaf. The layer computes nothing itself: every value
comes from an engine operation on a leaf, except the `DensePythonMatrix` paths (Python arithmetic)
and the NumPy round trip of view tiles (C-3).

## Findings

**C-1 (S2 major) The result of a block operation cannot be used in another block operation:
`(L @ R) @ R`, `(L + R) + R`, `L @ (R @ R)`, `g @ g @ g` all raise `TypeError`.** [repro]
- Where:
  - `_leaf_matmul` (`blockmatrix.py:22-30`) and `_leaf_elementwise` (33-43) pass a `ThunkBlock`
    leaf through to `a @ b` / `a + b`.
  - `ThunkBlock` (`thunks.py:33-135`) defines no operators, and the engine operators do not accept
    it.
- Repro (t6.py), L, R = 1x1 grids of 2x2 float64 matrices, g a 2x2 grid:
  ```
  (L@R)@R, pc.matmul(L@R, R)  -> TypeError: unsupported operand type(s) for @: 'ThunkBlock' and 'DenseMatrix'
  L@(R@R)                     -> TypeError: ... 'DenseMatrix' and 'ThunkBlock'
  (L+R)+R, (L@R)+R            -> TypeError: ... for +: 'ThunkBlock' and 'DenseMatrix'
  g@g@g                       -> TypeError (same)
  X = L@R; np.asarray(X); X@R -> TypeError (evaluating first does not help)
  ```
- Scenario: any expression with two block operations, e.g. a block power or `A @ B + C`. The
  results can only be read, exported or saved. Matrix Guide:112 and Block Matrices.md:98 list
  "feeding a thunk block into another op" as an evaluation trigger, so the docs promise this.
- Fix: one `_leaf_operand(x)` called at the start of every `_compute`. It turns a `ThunkBlock` into
  `x.materialize()` and a `SubmatrixView` into an engine window (C-3). Then pin the inner thunk's
  inputs as well (C-5), or a cached outer result goes stale silently once this works.
- Regression test: the six expressions above against NumPy, including evaluation before reuse.

**C-2 (S2 major) Element-wise operations on grids with different partitions fail; the one case that
runs returns Python tiles that export as an object array and cannot be saved.** [repro]
- Where:
  - `block_add` etc. (`blockmatrix.py:478-691`) refine both operands into `SubmatrixView` tiles
    and call `_leaf_elementwise`.
  - `SubmatrixView` has only `__add__` and `__matmul__` (`submatrix_view.py:131-137`), and the
    engine operators reject it, so `engine - view`, `view * engine`, etc. raise.
  - `view + engine` builds a `DensePythonMatrix` element by element (`_dense_from_get`, 17-25;
    `DensePythonMatrix.__add__`, `dense_python.py:48-55`).
- Repro (t2.py, t3.py, t7.py), `L = [[A[:, :2], A[:, 2:]]]`, `R = [[C]]` (4x4):
  ```
  L + R, L - R, L * R, L / R      -> TypeError: unsupported operand type(s) for +: 'DenseMatrix' and 'SubmatrixView'
  R - L, R * L, R / L             -> TypeError: ... 'SubmatrixView' and 'DenseMatrix'
  R + L                           -> tiles are DensePythonMatrix
    np.asarray(R + L)             -> shape (1, 2), dtype object, elements DensePythonMatrix(...)   (silent)
    pc.to_numpy(R + L)            -> the same object array
    pc.save(R + L, p)             -> TypeError: save: not a PyCauset matrix or vector: DensePythonMatrix
  ```
- Scenario: adding a correction stored as one block to a grid, or any two grids built separately.
  The one case that runs gives the user an object array with no error.
- Fix: resolve view tiles to engine windows before the leaf operation (C-1's `_leaf_operand`,
  C-3's windows). Delete `SubmatrixView.__add__` / `__matmul__` and `DensePythonMatrix`. Until
  windows exist for a leaf class, raise at operation time, naming the leaf class, the operation and
  the cut.
- Regression test: all eight cases with engine leaves against NumPy, plus `np.asarray` and
  `pc.save` of the results. Replace `ToyMatrix` in `test_block_add_aligns_partitions_by_refinement_union`
  with engine matrices.

**C-3 (S2 major) Refined matmul goes through NumPy: every cut tile is exported and imported again,
is subject to the export ceiling, is held in RAM, and fails for structured leaves.** [repro]
- Where:
  - `refine_partitions` makes a `SubmatrixView` for every cut leaf (`blockmatrix.py:294-297`).
  - `_leaf_matmul` sends it to `pc.matmul`. `ops.matmul` imports non-engine operands
    (`ops.py:79-82`) with `_import_operand`, that is `np.asarray(view)` (86-93), which calls
    `SubmatrixView.__array__` (`submatrix_view.py:74-85`): an engine slice exported to NumPy, then
    `Matrix(arr)`.
  - For non-engine sources (a nested `BlockMatrix`, a `ThunkBlock`) the export is a Python
    double loop of `source.get` (84).
- Repro (t1.py, t4.py, t9.py, t10.py, t13.py):
  ```
  [[A]] @ [[X[:2]], [X[2:]]] (6x6)   -> correct, 2 SubmatrixView exports + re-imports
  same, set_export_max_bytes(200), 8x8 leaf
                                     -> RuntimeError: Export to NumPy (256 bytes) exceeds the ceiling
                                        (the aligned product and A[:, 0:4] @ X run in the engine)
  leaf diagonal / identity / symmetric / causal (triangular bool), refined
                                     -> NotImplementedError: slicing is not supported for <class> matrix
  dense complex_float16 leaf, refined -> NotImplementedError: slicing is not supported ... complex_float16
  nested BlockMatrix leaf cut (3x6)  -> 18 Python BlockMatrix.get calls to build the tile
  L @ ndarray with L split           -> AttributeError: 'numpy.ndarray' object has no attribute 'get'
  ```
  The same products without a cut work for every structure (t4.py), so a partition mismatch decides
  whether a structured grid can be multiplied.
- Scenario:
  - Block matrices exist to keep large and structured leaves out of RAM and in their class.
  - A cut tile of a disk-backed leaf is copied into RAM twice and fails under the export ceiling.
  - A cut diagonal or causal leaf fails outright.
  - The atlas would classify the path as "numpy-fallback" (`export_guard.export_count` rises).
- Fix:
  - Refine an engine dense leaf to its engine window (`blk[r0:r1, c0:c1]`, zero-copy,
    copy-on-write).
  - Split a structured leaf by structure: a diagonal or identity tile on the diagonal is diagonal,
    and the off-diagonal tiles are zero matrices of the leaf's dtype; a triangular tile on the
    diagonal is triangular, and the tiles on the other side are zero. Otherwise give structured
    classes engine windows (3.2), or raise at refine time naming the leaf.
  - Refine a nested `BlockMatrix` recursively into a sub-grid.
  - Make a view of a thunk a lazy window that is resolved after `materialize`.
  - Delete the `__array__` element loop.
- Regression test: the repro lines above. Count `export_guard.export_count` around the product and
  expect 0.

**C-4 (S2 major, NumPy oracle) Mixed-dtype grids promote per tile, so a block result differs from
NumPy on the assembled matrix; the documented metadata promotion does not exist.** [repro]
- Where: `_leaf_elementwise` / `_leaf_matmul` (`blockmatrix.py:22-43`) use each tile's own dtypes.
  Export (`__array__`, 404; `export_to_numpy`, `export_guard.py:176`) assembles with `np.block`,
  which promotes every leaf to the common dtype.
- Repro (t3.py), `a8 = int8 2x2 of 100`, `f32 = float32 2x2 of 1`:
  ```
  np.asarray([[a8, f32]] + [[a8, f32]])[0]  -> [-56, -56, 2, 2]      (NumPy on the assembled matrices: [200, 200, 2, 2])
  [[f32, a8]] @ [[f32], [a8]]               -> OverflowError: Integer matmul overflow
                                               (NumPy on the assembled matrices: float32 20002)
  ```
  So `np.asarray(L + R) != np.asarray(L) + np.asarray(R)`, and a grid's export has one dtype while
  its operations use several.
- Docs:
  - Block Matrices.md:107 and matmul.md:64 say "Accumulator dtype is chosen from metadata before
    evaluation by folding the add-result dtype across term dtypes". No such code exists.
  - Matrix Guide:70 promises "no surprise dtype promotion".
  - Block Matrices.md:93-94 and 108 say promotion is per leaf product.
- Scenario: a grid of int8 counts beside float32 weights. Some tiles wrap or raise, while the
  "same" matrix in NumPy does not.
- Fix (decide; recommended first):
  - Give `BlockMatrix` a real dtype: the engine's result dtype over the leaves (np.block's rule,
    which is the engine's promotion). Have every operation compute its result dtype from both
    grids' dtypes before evaluation, and have each tile cast its leaf operands to it (`cast_to`
    in the engine, which is lazy for scale views). This is what the docs already describe.
  - Or keep per-tile semantics as a deliberate deviation. Then document it on the NumPy
    differences page and in to_numpy.md (the export promotes, the operations do not), and remove
    the folding sentence.
- Regression test: the two lines above against NumPy on `np.asarray` of the operands, plus a
  complex / float grid (complex tiles today, t12.py) and an int / bool grid.

**C-5 (S3 minor) Staleness: 3.9 C-4 is fixed, but thunk and nested-grid leaves are not pinned, the
snapshot rule differs between flat and nested grids, and the thunk cache is still a result cache
outside DerivedCache.** [repro]
- Status of 3.9 C-4: **fixed**. `_get_version` reads `_native._storage_version` (`thunks.py:12-24`).
  The 3.9 repro (evaluate, `a[0, 0] = 7`, read or save) now raises `StaleThunkError` for both
  (t5.py).
- Remaining:
  - A `ThunkBlock` has no version (`_get_version` returns None), and a `BlockMatrix`'s version
    counts only `set_block` (`blockmatrix.py:233-250`). The outer thunk therefore pins neither a
    thunk leaf's inputs nor a nested grid's leaves.
  - Today a cached nested result still raises, because the inner product's own thunks pin the leaf
    (t11.py). Once C-1 is fixed, an outer cache over a thunk leaf would be served stale silently.
  - Flat and nested grids disagree when a leaf is written before the first evaluation (t11.py):
    ```
    flat:   out = [[a]] @ [[b]]; a[1,1] = 5; out.get(0,0)     -> StaleThunkError
    nested: o = [[[[a]]]] @ [[b]]; a[0,0] = 100; o.get(0,0)   -> 106.0 (computed with the new value)
    ```
  - "Snapshot-at-creation" takes no snapshot. Any write to any input before the first read makes
    the whole result unusable, and the message does not say to recompute. `StaleThunkError` is not
    public.
  - CLAUDE.md forbids result caching outside `DerivedCache`. `ThunkBlock._cache` (`thunks.py:70`)
    is the remaining Python cache. It is documented (Block Matrices.md:58-66), but the exception is
    not recorded in `review/features/DERIVED_CACHE.md`.
- Fix:
  - Give `ThunkBlock` and `BlockMatrix` a `version` that folds their pins and leaves (or make
    `_check_stale` recurse), so one rule covers flat, nested and chained grids.
  - Write the cache exception into DERIVED_CACHE.md (or drop the cache and recompute per access
    of a tile).
  - Export `StaleThunkError`, and say in its message: "recompute the operation".
- Regression test: write a native leaf after evaluation (missing from `tests/blockmatrix`; only the
  Python `version` toy is tested); nested first-evaluation after a write; a chained product after
  C-1.

**C-6 (S3 minor) Export-guard gaps for block matrices (3.9 C-6 follow-up).** [repro]
- `estimate_materialized_bytes` sums the leaves (`export_guard.py:98-102`), but a thunk leaf's
  dtype is the label `"thunk"`, so the estimate is None and the total check is skipped. Each leaf is
  then checked on its own. With `set_export_max_bytes(200)`, a grid of two 128-byte thunk leaves
  exports 256 bytes (t12.py).
- `pc.to_numpy(product, allow_huge=True)` still raises the ceiling error: `ThunkBlock.__array__`
  (`thunks.py:111-116`) does not pass `allow_huge` down (t7.py). It works for plain grids.
- `np.asarray(bm, copy=False)` returns a copy without an error (t7.py); NumPy 2's protocol
  expects `ValueError`. The same holds for `SubmatrixView` and `ThunkBlock`.
- `BlockMatrix.__array__(dtype=...)` converts without counting the target size (404-405);
  `export_to_numpy` counts it.
- Fix:
  - Estimate a thunk from its shape and the result dtype (C-4 gives one), or evaluate its leaves'
    dtypes from metadata.
  - Route `__array__` of all three classes through `export_to_numpy`, which passes `allow_huge`
    and handles `copy` and `dtype`.

**C-7 (S3 minor, NumPy behind a PyCauset object) `ndarray @ bm`, `ndarray + bm` compute in NumPy,
and `pc.add(bm, bm)` / `pc.multiply` silently densify into a dense engine matrix.** [repro]
- Where:
  - `BlockMatrix` has `__array__` but neither `__array_ufunc__ = None` nor `__array_priority__`,
    which the engine classes set (t8.py: native `__array_ufunc__` None, priority 1e6). So NumPy's
    operator exports the grid and computes itself.
  - `ops.elementwise` (`ops.py:103-111`) imports a `BlockMatrix` through `_import_operand`
    (`np.asarray`), while `ops.matmul` routes it to the block path.
- Repro (t2.py, t8.py):
  ```
  np.ones((4,4)) @ L, np.ones((4,4)) + L  -> numpy.ndarray (1 export of L)
  pc.add(L, L), pc.multiply(L, L)         -> DenseMatrix (4 exports), not a BlockMatrix
  ```
- This breaks "once block, always block" and "no silent densify", which are both in the docs.
- Fix: set `__array_ufunc__ = None` and `__array_priority__` on `BlockMatrix` (then
  `__rmatmul__` / `__radd__` run). Route `BlockMatrix` operands in `ops.elementwise` to the block
  functions, as `matmul` does.

**C-8 (S3 minor) API surface: no scalars, transpose, slicing, vectors or NumPy-style indices; docs on
three pages promise block-aware slicing.** [repro] (t2.py, t11.py, t13.py)
- Missing operations:
  ```
  bm * 2, 2 * bm, bm + 1      -> TypeError: BlockMatrix blocks must be matrix-like (rows/cols or shape)
  ```

**C-11 (S4 nit, performance) IO hints work against reuse; accumulation allocates a temporary per k.**
[citation]
- `block_matmul`'s `_compute` (`blockmatrix.py:444-462`):
  - It discards `a` and `b` after every product. They are the user's input leaves, reused by
    every other output block of the same row or column, so file-backed inputs are re-read once per
    output block.
  - The element-wise thunks discard `out` (517, 573, 625, 677) just before returning it. The
    caller reads it next.
  - Every thunk prefetches the whole storage of every leaf (`SIZE_MAX`), including leaves of
    which it uses one tile.
- `acc = acc + prod` allocates K-1 full-size temporaries per output block. An in-place `+=` (or a
  matmul with beta = 1 in the engine) would allocate none.
- Fix: discard only temporaries (`old_acc`, `prod`). Prefetch only the tile the next product reads.
  Accumulate in place.
