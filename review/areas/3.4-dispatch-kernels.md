## What it does
Every engine entry function (`src/math`) reaches its kernel through
`ComputeContext::instance().get_device()`. That is an `AutoSolver`, which routes to a GPU device
when one is loaded (never, in R1: CUDA is in `experimental/`) and otherwise forwards to
`CpuDevice`. `CpuDevice` in turn forwards every one of its 26 methods to a `CpuSolver` member.
`ComputeContext` also tries `dlopen("libpycauset_cuda.so")` the first time it is used.

`CpuSolver` holds the kernels, each with a contract comment:
- matmul: dense `T x T` for float, complex and integer T. Integers use exact float64 BLAS when the
  measured bound allows it, otherwise 128-bit accumulation. There are also an upper-triangular
  kernel, bit x dense, and bit x bit popcount kernels.
- element-wise `+ - * /`: a packed same-structure path, then a plain flat loop, then a strided
  view reader, then the typed row reader, and finally a per-element virtual path.
- matrix-vector products for bit closures and structured matrices (packed gather / scatter).
- dot (BLAS / popcount), Frobenius and L2 norm (fixed blocks), and `compute_k` (`C (aI + C)^-1`
  over the causal bits).
- LAPACK kernels (`?gesdd`, `?getrf` + `?trsm`, `?gelsd`, `?syevd`/`?heevd`, `?geev`, `?potrf`,
  `?gelqf`/`?orglq`, `?getrf`). All of them except eig and LU run column-major on the row-major
  buffer, so LAPACKE does not transpose.
- Spectra Krylov eigensolvers, with `matrix_vector_multiply` as the operator; skew eigen through
  `?heevd` (values) or `?geev` (vectors).

Parallelism comes from a process-wide `ThreadPool` (`ParallelFor` hands out chunks dynamically
and runs loops of fewer than 32 items inline), from OpenBLAS's own threads, and from two OpenMP
regions.

## Findings

**C-1 (S1 critical, silent wrong values) The bit-vector dot counts padding bits: `pc.dot(~u, ~u)`
is 64 for a length-5 vector.** [repro]
- Where: `CpuSolver.cpp:128-141`. The popcount loop runs over `(n + 63) / 64` whole words and does
  not mask the bits past `n` in the last word.
  - `bitwise_not` (math/Bitwise.cpp) sets those bits.
  - Every other bit reader masks them: `bit_popcount_matmul` (CpuMatmul.cpp:211-214),
    `bit_x_dense_kernel` (672), `sum`, `norm`, export.
  - So the result is wrong only through `dot` and vector `@`.
- Repro (`t13_bitdot.py`, `t14_bitnot.py`):
  ```
  u = pc.vector(np.zeros(5, bool))
  pc.dot(~u, ~u), (~u) @ (~u)  -> 64, 64      (count of common elements: 5; pc.sum(~u) = 5)
  w = pc.vector(np.zeros(130, bool)); pc.dot(~w, ~w) -> 192   (expected 130)
  pc.dot(~u, ones(5)) -> 5 (correct: the padding of `ones` is zero)
  (~M) @ (~M).T for a 2 x 5 bit matrix -> all 5 (correct: matmul masks)
  ```
- Scenario: counting the common elements of two complemented relations (for example "neither
  in the past nor in the future" sets of causal-set elements), with `~` on a bit vector. The
  count is off by up to 63 per complemented operand pair, and nothing warns.
- Fix:
  - In the kernel, mask the last word with `n % 64`: the kernel must not trust bits past `n`.
  - Also decide the storage invariant (padding bits are zero) in `bitwise_not`, so the next
    reader that trusts storage is safe too (3.2 / 3.6 owners).
- Regression test: the four lines above, for n = 5, 64, 65 and 130, against
  `int(np.sum(a & b))`.
- **Fixed (session 9):** the last word is masked (`test_3_4_C1_bit_dot_ignores_padding_bits`).

**C-2 (S2 major, hang) After `fork()` (Linux `multiprocessing`'s default before Python 3.14) the
first parallel kernel in the child waits forever.** [repro]
- Where:
  - `ParallelUtils.cpp:24-60`: the pool's workers are created once, and a forked child has only
    the forking thread. `ParallelFor` enqueues tasks no one runs, then blocks on their futures.
  - `CpuSolver.cpp:135` (the bit dot's `#pragma omp parallel for`): libgomp is not fork-safe
    either.
- Repro (`t2_fork.py`, `t3_mp.py`, `t4_ompfork.py`), with `pc.set_num_threads(2)`:
  ```
  parent: A + B (1024 x 1024)  -> fine (pool created)
  child after os.fork(): 4 x 4 add fine (inline); 1024 x 1024 add -> no return, killed by SIGALRM after 5 s
  multiprocessing.get_context("fork").Pool(1).map(lambda: A + A) -> no result after 5 s
  child after fork: pc.dot of two 5000-element bit vectors (OpenMP) -> killed after 5 s
  ```
- Scenario: a parameter sweep over sprinklings with `multiprocessing.Pool` (the common way to
  use all cores from Python) after any PyCauset work in the parent. The workers hang
  silently, with no error and no CPU use. (Python itself prints a DeprecationWarning about fork
  in a threaded process, which most users ignore.)
- Fix:
  - Register `pthread_atfork(nullptr, nullptr, child)`. The child handler marks the pool dead
    (abandons the old `std::thread` objects without joining them, resets the queue and mutex),
    and `instance()` rebuilds it lazily. Alternatively, record the creator's `getpid()` and
    rebuild on mismatch.
  - Replace the two OpenMP `parallel for` regions with `ParallelForRange`. The engine then never
    starts a libgomp team, and the whole OpenMP runtime is only needed for `omp simd`
    (`-fopenmp-simd`).
  - Document fork / spawn in the Performance Guide.
- Regression test: fork, run a 1024 x 1024 add and a bit dot in the child under a 10 s alarm,
  check the exit status.
- **Fixed (session 9):** `ThreadPool::instance()` records the pid that built the pool; a forked
  child builds its own (the parent's is abandoned, its threads do not exist there). The two
  OpenMP regions (bit dot, complex fallback dot) are serial, so the engine starts no libgomp
  team. `test_3_4_C2_parallel_kernels_run_after_fork`.

**C-3 (S2 major, wrong values) `eig_skew` returns eigenvectors that are not orthonormal on
degenerate spectra, so the Sorkin-Johnston `W` its documentation builds from them is wrong.**
[repro]
- Where: `CpuIterative.cpp:309-357` uses the general `?geev`. For a normal matrix with a repeated
  eigenvalue, `?geev`'s vectors span the eigenspace but are not orthogonal within it.
  `eigvals_skew` (232-285) already uses `?heevd` on `H = iA`, which is Hermitian, so its
  eigenvectors would be orthonormal.
- Also, the order:
  - `eigvals_skew`'s pair loop (274-280) advances past a pair only when it swapped it, so pairs
    misalign.
  - `eig_skew` sorts by `|w|` with no tie-break (347-349).
  - The two functions therefore return a different order for the same matrix.
- Repro (`t9_svd_skew.py`): A = Q (J ⊕ J ⊕ 2J) Q^T, J = [[0, 1], [-1, 0]], Q random orthogonal:
  ```
  eigvals_skew(A, 6) -> [2j, -2j, 1j, -1j, -1j, 1j]    (its comment: +i first in each pair)
  eig_skew(A, 6)[0]  -> [2j, -2j, 1j, -1j, 1j, -1j]
  max |V^H V - I|    -> 0.204
  W = V+ diag(Im w+) V+^H vs the same from numpy.linalg.eigh(iA): max difference 0.078
  ```
- Scenario: `eig_skew` is documented as "the diagonalization used to build the Sorkin-Johnston
  vacuum W from the Pauli-Jordan matrix". Pauli-Jordan matrices of symmetric causal sets (a
  lattice, products of chains) have degenerate nonzero eigenvalues, and then W is wrong with no
  warning.
- Fix:
  - `eig_skew` = `?heevd('V')` on `iA`: eigenvalues `-i mu`, orthonormal eigenvectors (and
    about 2x faster than `?geev`, as the `eigvals_skew` comment measured).
  - One shared sort with a total order (|imag| descending, then imag descending) for both
    functions.
  - Update `eig_skew.md`, which still says "falls back to NumPy" and "dgeev".
- Regression test: the matrix above. Check `V^H V = I` to 1e-12, equal order in both
  functions, and W against `eigh(iA)`.
- **Fixed (session 9):** both functions use `?heevd` on `-iA` (`skew_hermitian_solve`) and one
  order (`skew_order`: |mu| descending, +i first within a pair or cluster);
  `test_3_4_C3_eig_skew_vectors_are_orthonormal_and_orders_agree` (V^H V = I and W against
  `eigh(iA)` to 1e-12).

**C-4 (S2 major, wrong values) `compute_k` ignores the view: `compute_k(C.T)` returns K of C;
`a = 0` returns inf / nan where the matrix is singular.** [repro]
- Where:
  - `CpuSolver.cpp:526-596` reads `C.data()` by stored rows. It never consults
    `is_transposed()`.
  - The binding (`bind_matrix.cpp:1030-1044`) calls the device directly, bypassing the entry
    (`LinearAlgebra.cpp:1323-1330`, dead), and checks only the class.
  - `num_threads` is accepted and ignored (532), although `compute_k_matrix.md` documents it.
  - There is no `debug_trace` tag (invisible to the atlas) and no test beyond the API surface.
- Repro (`t8_k.py`), random 6 x 6 causal C, NumPy `C @ inv(aI + C)`:
  ```
  compute_k(C, 2.0)    -> max error 0.0
  compute_k(C.T, 2.0)  -> max error 0.5   (C.T is transposed; the result is K of C, upper)
  compute_k(C, 0.0)    -> contains inf/nan (NumPy: LinAlgError: Singular matrix)
  ```

- Scenario: a lower-triangular (past-pointing) causal matrix, which `C.T` gives in O(1), passed to
  `compute_k`. The result is silently the future-pointing K.
- Fix:
  - An entry function that validates `a != 0` (raise as singular) and the class.
  - For a transposed C, return the transposed K. Since `(aI + C^T)^-1` commutes with `C^T`,
    `K(C^T) = K(C)^T`: an O(1) view.
  - Drop `num_threads` or honour it. Add a trace tag and an atlas row.
- Regression test: the three lines above, against NumPy.
- **Fixed (session 9):** the entry `compute_k_matrix(C, a)` (LinearAlgebra.cpp) checks the

  (internal; `pc.compute_k` is the public name); `num_threads` is gone; trace tag

**C-11 (S3 minor, determinism) dot and norm depend on the BLAS thread count.** [repro]
- Where:
  - `cblas_ddot` in `CpuSolver::dot` (113) and in the norm's fixed blocks (663). OpenBLAS splits
    a `ddot` of more than about 10^4 elements across its own threads.
  - The protocol (Step 4) requires sums in fixed blocks independent of the thread count. The
    norm's 2^16-element blocks are fixed, but each block's `ddot` is not.
  - Pool workers calling threaded `ddot` also nest pools (4 x 4 threads here).
- Repro (`t16_det.py`, 1,000,003 elements of mixed magnitude):
  ```
  1 thread : dot -5.630301494273024e+16, norm 54163516849.50964
  2 threads: dot -5.630301494274642e+16, norm 54163516849.50967
  ```
- Fix:
  - Fixed blocks with a single-threaded inner product: an unrolled loop, or OpenBLAS 0.3.27's
    `openblas_set_num_threads_local(1)` inside the pool workers.
  - `dot` uses the same block scheme as the norm.
- Regression test: run in subprocesses with 1 and 2 threads and compare bit-identical results.
- **Fixed (session 9):** dot and norm sum fixed 8,192-element blocks (OpenBLAS runs a `?dot`
  of at most 10,000 elements on one thread) in the pool, combined in block order; scaled views
  use a four-accumulator `omp simd` loop. `test_3_4_C11_dot_and_norm_do_not_depend_on_the_thread_count`.
  Cost (timing run of session 9): the float64 dot of 10^6 elements is about 0.19 ms against
  NumPy's 0.05-0.09 ms (whole-vector threaded `ddot` was 0.12 ms), and 190 norm cells are below
  0.9x (112 before; NumPy's own time varies 2x between runs here). Open for the speed phase:
  fewer pool tasks per call, an AVX2 path for the scaled loop.

**C-16 (S4 nit, performance) Smaller waste.** [citation]
- `bit_popcount_matmul` (CpuMatmul.cpp:183-191, 220):
  - It builds B^T serially through `b.get(i, j)`.
  - It writes C through `c.set(i, j, v)` from all pool threads. Each `set` calls
    `ensure_unique()`, and so `bump_version()`, which does an atomic store plus a `fetch_add` on
    one global counter (`MemoryMapper.hpp:66-67, 100-103`). That is m x n contended atomic
    operations per product.
  - Fix: write `c.data()` directly after one `ensure_unique()`, and transpose B with word
    operations.
- `eig_t` / `lu_t` (CpuLinalg.cpp:146-158, 263-266) use `LAPACK_ROW_MAJOR`, which transposes in
  and out (F-108 removed this elsewhere). For eigenvalues only, the column-major `A^T` has the
  same spectrum.
- `int_matmul_via_dgemm` (CpuMatmul.cpp:518) allocates three dense double heap buffers, 8x an
  int8 operand. Protocol §7 asks for work buffers placed as storage. It is gated only by
  `can_fit_in_ram`.
- `ParallelFor`'s calling thread idles while the pool works. Letting it take chunks saves one
  wake-up and one core.
- The bit dot starts an OpenMP team even for a single word.
- The `dot_complex` typed path is a serial loop.
- `eigvals_arnoldi`'s dense fallback (CpuIterative.cpp:187-202) reads per element.
- The packed matvec's fused loop vectorises only through `#pragma omp simd`. Without OpenMP
  (optional in CMake, line 360; macOS without libomp) it loses that (its comment: 0.3x NumPy).
  Always compile with `-fopenmp-simd`.

**C-18 (S4 nit, robustness) Contracts not asserted; CPU feature detection incomplete.** [citation]
- `svd_dense`, `solve_dense` and `lstsq_dense` (CpuSolver.cpp:787-913) read `data()` without

- The integer matmul kernels should assert factor 1 rather than compose it.
- `has_avx2` / `has_avx512_vpopcntdq` (CpuElementwise.cpp:96-121, CpuMatmul.cpp:93-126) test

  is released (C-5). Use `__builtin_cpu_supports("avx2")` /

  transposed B built beside it has zero padding (CpuMatmul.cpp:203-214). Say so, or mask.
