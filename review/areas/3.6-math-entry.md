## What it does
Every Python operator and `pycauset.f()` lands in one C++ entry function per operation:
`add` / `subtract` / `elementwise_multiply` / `elementwise_divide` (broadcast, resolve the
dtype, structure rules, then the device kernel), `dispatch_matmul` (rules R1 identity, R2
bit-packed, R3 triangular, R4 diagonal, R5 dense), `matrix_vector_multiply` /
`vector_matrix_multiply` (a vector as an n x 1 / 1 x n view, plus a structured and a closure
rule), `scalar_op` (one entry for `A op s`; O(1) scale views for float/complex and integer
factors, typed kernels otherwise), `inverse`, `solve`, `lstsq`, `cholesky`, `lu`, `qr`,
`svd`, `pinv`, `eig*` (normalise with `to_dense` to NumPy's LAPACK dtype, then a LAPACK kernel),
`determinant` / `slogdet` (LU pivots, with identity / diagonal / triangular rules), `sum` /
`trace` (exact 128-bit integers, double floats), `matrix_norm` / `vector_norm` /
`matrix_rank`, `bitwise` / `bitwise_not`, `outer_product`, `cross_product`. View semantics
come from `view_value` (ViewValue.hpp) through the typed readers `read_rows` / `read_wide` /
`raw_rows`. Scalar results of whole-matrix computations are cached in `DerivedCache`.
`ops.py` is thin glue: array-like import, BlockMatrix routing, and three operations computed
in Python (`matrix_power`, `cond`, `solve_triangular`'s class check).

   closure matvec rule is the out-of-core path for C - C^T, but `vector_matrix_multiply`

6. Concurrency: no shared state. `cached()` relies on the mapper's version (3.1 C-15, fixed).
7. Performance:

   - `solve_triangular` runs a full LU (O(n^3)) on a triangle.
8. Duplication:
   - `add`, `subtract` and `elementwise_multiply` (144-240) are the same 30 lines three times.
     `elementwise_divide` (242-261) is a fourth copy without the structure resolver.
   - Complex-dtype predicates are written five times in this file alone (`mm_complex`,

## Findings

**C-1 (S2 major, wrong contract at the int64/uint64 edge) Integer matmul wraps silently at 2^63,
and uint64 values >= 2^63 raise.** [repro]
- Where:
  - Dense: `CpuMatmul.cpp:383` (`const int64_t term = val_a * val_b;`, unchecked signed
    overflow, which is UB in C++). The int64 accumulator in the same kernel cannot hold
    uint64 values >= 2^63.
  - R4 diagonal: `LinearAlgebra.cpp:780` compares the 128-bit product as a double against
    `hi`, which rounds to 2^63 / 2^64.
  - Triangular: `CpuMatmul.cpp:592-638` (int64 `Acc`, unchecked multiply).
- Repro (t6.py and inline):
  ```
  int64 [[2**31]] @ [[2**32]]            -> [[-9223372036854775808]]   (documented: OverflowError)
  int64 [[2**32]] @ [[2**32]]            -> [[0]]                      (cpu.matmul.i64)
  diag int64 2**62 @ diag 2              -> [[-9223372036854775808, 0], [0, 1]]
  diag uint64 2**63 @ diag 2             -> [[0, 0], [0, 1]]
  triangular int64 2**32 @ itself        -> [[0, 0], [0, 1]]
  uint64 [[2**63]] @ [[1]]               -> OverflowError (fits; NumPy: [[9223372036854775808]])
  (I_uint64 * (2**64-1)) @ ones          -> OverflowError (NumPy: 2**64-1)
  ```
- Scenario: path counts, combinatorial or hash-like integer data in int64 / uint64. The values
  happen to equal NumPy's wrap, but DType System §5.1 promises "throws OverflowError when the
  final result does not fit", and the C++ is undefined behaviour that an optimiser may
  exploit.
- Fix:
  - Multiply with `__builtin_mul_overflow` (or in `__int128`) in all three integer kernels.
  - Accumulate uint64 in `unsigned __int128`.
  - In R4, compare the `__int128` product against `numeric_limits<R>` as integers, not
    doubles.
- Regression test: the six lines above.

**C-2 (S2 major) Any NaN makes every LAPACK operation raise "illegal argument" (and print to
stderr); `cond` turns that into inf; 0 x 0 cholesky/eigh/eigvalsh fail the same way.** [repro]
- Where:
  - The LAPACKE high-level wrappers in `CpuLinalg.cpp` / `CpuSolver.cpp` check their input
    for NaN and return info = -4, which the kernels report as "illegal argument" (e.g.
    `CpuLinalg.cpp:292`, `CpuSolver.cpp:862`).
  - The xerbla messages (`** On entry to DLASCL parameter number 4 had an illegal value`) go
    to stderr (F-109 forbids engine output).
  - 0 x 0: the entries (`LinearAlgebra.cpp:854`, `1216`, `1227`) pass n = lda = 0, and
    LAPACKE requires lda >= 1.
- Repro (t5.py, t3.py, t11.py), A = [[nan, 1], [1, 2]]:
  ```
  det, slogdet, inv, solve -> RuntimeError: ... illegal argument to ?getrf   (NumPy: nan values / LinAlgError for inv)
  qr                       -> RuntimeError: qr: ?gelqf failed               (NumPy: nan entries)
  cholesky, eigvalsh       -> RuntimeError: illegal argument               (NumPy: values)
  svd/pinv/rank/norm(2)    -> RuntimeError: SVD: illegal argument to gesdd   (NumPy: LinAlgError)
  pc.cond(A, 1)            -> inf                                            (NumPy: nan)
  cholesky / eigh / eigvalsh of 0x0 -> RuntimeError: illegal argument        (NumPy: empty)
  ```
- Scenario: a NaN from a 0/0 upstream. The user gets a message that blames PyCauset's
  arguments, a stderr dump, or with `cond` a plausible wrong number.
- Fix:
  - Call `LAPACKE_set_nancheck(0)` once at start-up, so NaN propagates as in NumPy, or use the
    `LAPACKE_*_work` entry points. Where NumPy raises (eig, svd), raise `ValueError` /
    LinAlgError-style "did not converge".
  - Route xerbla to an exception (OpenBLAS: `xerbla` override).
  - Give the entries an n == 0 rule (empty results).
  - In `cond`, catch only the singular case (a dedicated exception type or message), not
    every `RuntimeError`.
- Regression test: each op on a NaN matrix and on 0 x 0, against NumPy.

**C-3 (S2 major, wrong values) `I(m x k) @ I(k x n)` is returned as an m x n identity.** [repro]
- Where: `LinearAlgebra.cpp:694-700` (R1). It checks neither that k >= min(m, n) nor squareness.
  `identity_times` (702-713) does check squareness.
- Repro (t1.py): `pc.IdentityMatrix(3, 2) @ pc.IdentityMatrix(2, 3)` gives `eye(3)`; NumPy gives
  `diag(1, 1, 0)`.
- Scenario: rectangular identities from `pc.identity([r, c])` (documented on identity.md) in
  projections.
- Fix: apply R1 only when k >= min(m, n) (the product is then the m x n identity). Otherwise
  return a diagonal (or dense) result with ones on the first min(m, k, n) entries.
- Regression test: the repro plus `I(2x3) @ I(3x2)` (correct today).

**C-4 (S2 major) Real factors are composed in complex arithmetic, and `A / s` is `A * (1/s)`:
`A * inf` gets factor `inf + nan j`, subnormal divisors give inf/nan.** [repro]
- Where:
  - `MatrixBase::scaled_clone(double)` (`MatrixBase.hpp:118`, `get_scalar() * f`): it is
    `complex * double`, so the imaginary part is `0 * inf = nan`.
  - `scalar_op` TrueDiv (`ScalarOps.cpp:668`).
- Repro (inline, t9 follow-up):
  ```
  A = pc.matrix([[1.0, 2.0]]);  (A * inf).get_scalar()  -> (inf+nanj)
  pc.sum(A * inf)                        -> (inf+nanj)   complex   (NumPy: inf, float)
  pc.det(pc.matrix(np.eye(2)) * inf)     -> RuntimeError: illegal argument   (NumPy: inf)
  pc.matrix([[1e-10, 1.0, 0.0]]) / 1e-310 -> [inf, inf, nan]   (NumPy: [1e300, inf, 0])
  pc.sum(that)                           -> (nan+nanj)          (NumPy: inf)
  ```
- Scenario: dividing by a tiny normalisation constant, or scaling by an infinite weight. The
  result has the wrong values and changes kind (real to complex).
- Fix:
  - Keep a real factor real: multiply the real part only when both factors are real.
    Better, store a real factor as a double beside an optional complex one.
  - Compute `A / s` as a division in the kernel (a `divide_by` view flag, or eager when
    `1/s` is not finite or not exact). This also closes F-126 C-14's ulp case.
- Regression test: the five lines above.

**C-5 (S2 major, NumPy oracle) Scale views compute in double and fold factors across
operations: float32 results differ from NumPy, and overflow / nan disappear.** [repro]
- Where:
  - `view_value` and `TypedReader` (`ViewValue.hpp:38`, `ScalarOps.cpp:318`) scale float32 /
    float16 / complex64 storage by a double factor.
  - Chained scalars fold (`scaled_clone`).

- Repro (t9.py and inline):

    dtype's range, or fold only exact (power-of-two) factors.

  - Otherwise document plainly that scaled float32 results are not NumPy's.

## Proposed changes
1. Integer matmul: checked products, 128-bit accumulation for uint64, integer comparison in R4
   (C-1). Regression tests at 2^63 / 2^64.
2. LAPACK entry hardening:
   - Turn off LAPACKE's NaN check (or use `_work` calls), so NaN propagates; raise NumPy's
     errors where NumPy raises.
   - Convert xerbla output to exceptions.
   - n == 0 rules for cholesky / eigh / eigvalsh.
   - `cond` catches only singularity (C-2).
3. R1 identity: a shape condition, otherwise a diagonal result (C-3).
4. Factors:
   - Keep real factors real (`scaled_clone`).
   - Make division a division, not `* (1/s)` (C-4).
   - Decide the float32 / folding contract against NumPy, not against PyCauset's eager path:
     round single factors to the storage dtype, and do not fold across possible overflow
     (C-5).
   - Update LAZY.md §3 and the guide.
5. Reductions: treat conj of non-complex as absent (C-6).
6. Broadcasting:
   - Fix the 0-axis sentinel.
   - Vector size-1 broadcasting.
   - NumPy operands for vectors.
   - `==` / `!=` with F-128 (C-7).
7. One dot entry in C++ with one integer rule shared with matmul's 1-D case. One `v @ M`
   orientation rule (C-8, C-9).
8. Skew / Arnoldi entries: validate the dtype and skewness, handle n == 0, add them to the
   atlas (C-10).
9. `materialize` = `cast_to` (C-11). Bool scalars as BIT operands (C-13).
10. Docs: matrix_power.md, matmul.md, the matmul docstring, DType System §5.1, the ScalarOps.hpp
    header, the Lazy guide (C-15).
11. Clean-up:
    - Merge the four element-wise bodies into one templated entry on the op.
    - Merge the four normaliser names into `to_dense(a, dt, keep_structure)` + `write_out`.
    - One dtype-predicate header.
    - Delete the dead lines in C-16.
    - Route `v @ closure` through the closure matvec (C-17).
12. Atlas: compare float32 / float16 scale views against NumPy's own arithmetic, not "with
    PyCauset's dtype" (atlas.py:206-207). Add empty, 1 x 1, NaN, non-square-identity and
    2^63-boundary cells (C-1 to C-5 were all outside it).
