## What it does (2-5 sentences)
Every matrix/vector is a `PersistentObject` owning a shared `MemoryMapper` plus view metadata
(complex factor, transposed, conjugated, and for dense matrices a window: logical shape + row/col
offsets). The concrete classes implement typed raw `get`/`set` in logical coordinates (raw =
without factor/conjugation), virtual `element_as_double/complex` (view rule applied), O(1)
`transpose` / `multiply_scalar` views (clones sharing storage), and `clone`. Writers call
`ensure_unique()` (copy-on-write and, since D.1, the derived-value cache's invalidation gate).
`BitClosureMatrix` is a lazy C +- C^T over a causal matrix's bits that materialises on first write.

## Findings

### C-1 (high) Writing to a lazy closure C ± C.T leaves stale derived values, and poisons other closures of C
- BitClosureMatrix.hpp:62-65 (`set` -> `materialize_in_place` -> `materialized_->set`; the
  closure's own storage version is never bumped) with DerivedCache.hpp:50-66 (`cached()` keys on
  `m.shared_mapper()`, which for a closure is C's bit storage shared by all closures of C).
- Repro (ran):
  ```
  C = pc.TriangularMatrix.random(6, p=0.5, seed=1); S = C + C.T
  pc.sum(S) -> 12; S[0, 1] = 7; pc.sum(S) -> 12   (NumPy: 26)
  S2 = C - C.T; pc.det(S2) -> 0.0; S2[0, 1] = 3; pc.det(S2) -> 0.0  (NumPy: 9.0)
  # poisoning: S = C + C.T; S[0,1] = 7; pc.sum(S) -> 26 (cached on C's bits)
  S2 = C + C.T  (fresh, true sum 12); pc.sum(S2) -> 26
  ```
- Fix: on materialisation, make the closure's `mapper_` the materialised storage (drop `bits_`,
  release C's bits), or have `set` call `ensure_unique()` on the closure before materialising and
  key the cache on the materialised storage afterwards. Regression test: write to the closure,
  then sum / det / trace / norm, and a fresh closure of the same C. (test_derived_cache.py only
  tests writes to C.)

### C-2 (high) Bool DenseVector writes skip copy-on-write: they leak into other objects and leave stale cached values
- src/vector/DenseVector.cpp:300-312 (`DenseVector<bool>::set` has no `ensure_unique()`).
- Repro (ran): `v = pc.vector(np.array([True, False, True])); w = v.T; w[0] = False` -> `v` is
  `[False, False, True]`. `v2 = pc.vector([True]*3); pc.sum(v2) -> 3; v2[0] = False;
  pc.sum(v2) -> 3` (true 2). The same applies to clones, `pc.load`ed snapshots and the
  eigenvalue-cache clones.
- Fix: `ensure_unique()` first in `set` (as every other writer). Test: write through `.T` / a
  clone of a bool vector, and sum after write.

### C-3 (high) Step slices and index arrays of a scaled or conjugated dense view drop the view
- src/bindings/matrix_indexing.hpp:259-318 (copies `mat.get()` = raw stored value; result factor 1).
- Repro (ran): `B = pc.matrix(np.arange(16.).reshape(4,4)) * 2.0`; `B[[0,1],[2,3]] -> [2, 7]`
  (NumPy [4, 14]); `B[::2, ::2] -> [[0,2],[8,10]]` (NumPy [[0,4],[16,20]]); int8 `(A*3)[::2,::2]`
  unwrapped; `C.conj()[::2, ::2]` and `C.H[[0,1],[1,2]]` return unconjugated values. Contiguous
  slices are views and are correct.
- Fix: read through the view (copy the window/positions as raw, then give the result the
  source's factor and conjugation, or read with view_value). Atlas "getitem" uses integer
  indices only: add step / fancy indexing x every view to the atlas.

### C-4 (medium) `HermitianMatrix * c` (c non-real) keeps the Hermitian class; the class no longer guarantees its structure
- SymmetricMatrix.hpp:172-174 via ScalarOps.cpp:689-692.
- Repro (ran): `H` Hermitian 2x2; `R = H * 1j` -> `HermitianMatrix`, values `[[1j, -3+2j],
  [3+2j, 4j]]` (not Hermitian); `H * (2+1j)` likewise; `SkewHermitianMatrix * 1j` stays
  SkewHermitian with Hermitian values. `R[0, 0] = 5j` raises "Diagonal of a Hermitian matrix must
  be real" although R's diagonal is imaginary. Today's kernels (eigvals, svdvals, solve, eigh,
  pinv, slogdet, R.H, R.T) still give NumPy's values; any kernel that trusts the class
  (Hermitian eigensolver, Cholesky) would not. Violates "structure is the class".
- Fix: structure rule at the scalar entry: Hermitian/skew-Hermitian x real stays; x pure
  imaginary swaps Hermitian <-> skew-Hermitian (O(1) view with the class changed); otherwise a
  complex symmetric-free result (dense). Same check for any future O(1) view constructor.

### C-5 (medium) `fill` ignores the view factor and conjugation; `set_identity` on a window half-writes then throws
- DenseMatrix.hpp:124-139, ComplexFloat16Matrix.hpp:88-103, bind_matrix.cpp:527-536 (no fold).
- Repro (ran): `(pc.matrix(a) * 2.0).fill(1.0)` -> all 2.0; int16 `(A*3).fill(5)` -> 15;
  complex `B.conj().fill(1j)` -> -1j. `A = pc.zeros((4,4)); W = A[0:2,0:2]; W.set_identity()` ->
  IndexError after W was zero-filled (DenseMatrix.hpp:146-148 loops to `base_rows()` with logical
  `set`).
- Fix: `fill`/`set_identity` reset the factor and conjugation (`set_scalar(1)`, conj false) after
  `ensure_unique()` (a fill overwrites every visible element, so no fold is needed for a full
  view; for a window, fold or reset only the window's own copy); `set_identity` loops over
  `rows()`/`cols()` and checks `rows() == cols()`.

### C-6 (medium) `SymmetricMatrix/AntiSymmetric/Hermitian.from_triangular(T)` ignores T's view
- SymmetricMatrix.hpp:202-211 (`source.get(i, j)` raw, upper positions only).
- Repro (ran): T with diag 1, T[0,1]=2, T[1,2]=3: `from_triangular(T * 2.0)` gives T's values;
  `from_triangular(T.T)` gives only the diagonal; `HermitianMatrix.from_triangular(Tc.conj())`
  is built from the unconjugated Tc.
- Fix: read through the view (typed reader / view_value) and reject a transposed (lower) source
  or read its upper triangle as the transpose. Test per view.

### C-7 (medium) Writes into views of Hermitian / skew-Hermitian matrices silently drop the view; complex structured views cannot be written
- src/bindings/matrix_indexing.hpp:629-636 (`stored` has no HERMITIAN/SKEW_HERMITIAN case: no
  element is folded, then :654-655 clear factor and conjugation) and :651 (complex element types
  read via `get_element_as_double`, which throws for complex).
- Repro (ran): `R = H * 2.0; R[0, 1] = 1` -> `[[1,1],[1,4]]` (expected `[[2,1],[1,8]]`);
  `R = H.T; R[0, 0] = 1` -> R becomes H (the transpose is lost); `K * 2.0` skew-Hermitian, write

### C-10 (low) Antisymmetric `-A` has a +0.0 diagonal; NumPy gives -0.0

### C-11 (low) Random bit matrices: unchecked p, 1e-4 "is it 0.5" heuristic, seed not recorded

### C-13 (low) Writing to a conjugated integer/bool vector or bool matrix raises

## Proposed changes (cleanup / Phase 4)
- One view rule: replace the remaining re-derivations (DenseMatrix, ComplexFloat16Matrix,
  ComplexFloat16Vector, DenseBitMatrix, TriangularBitMatrix, DenseVector<bool>) by `view_value`
  (C-9).
- One fold for writes, owned by the object model rather than the bindings: a `MatrixBase::
  fold_view()` that reads raw storage through `view_value` for every class (fixes C-5, C-7, C-13).
- BitClosureMatrix: on materialisation swap `mapper_` to the materialised storage and drop
  `bits_` (C-1); then closures need no special "materialized" checks in readers either.
- Delete dead API: `set_element_as_double`/`set_element_double` (all classes),
  `multiply_scalar(int64_t)` (all), the bit classes' and BitClosure's `multiply_scalar`,
  `DenseBitMatrix::elementwise_multiply` declaration, `MatrixBase::spill_to_disk(filename)`,
  DiagonalMatrix's protected constructors and `virtual` accessors, ComplexFloat16Vector's
  file-copy transpose branch, ObjectFactory::clone_vector's UNIT_VECTOR row, the ignored
  `result_file` parameter of `transpose`/`multiply_scalar`, DenseMatrix's `using
  MatrixBase::operator=`.
- `MatrixBase::shared_mapper()` should return `const std::shared_ptr<MemoryMapper>&` (or be
  removed in favour of PersistentObject's), matching DerivedCache's assumption.
