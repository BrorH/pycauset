## Answer to the plan's question

**Yes, out-of-core is mmap paging.** No code in the engine reads or writes a file explicitly
(no `pread`, no async I/O). No operation issues a prefetch or discard hint; only the Python
block-matrix layer does. Operations fall into three groups:

| How it runs on file-backed operands | Operations | Evidence |
|---|---|---|
| **Kernel runs on the mapped pages** (OS paging; no RAM copy) | every element-wise op, scalar ops, matmul of every structure and dtype outside the next row, matvec, `eigvals_arnoldi`, reductions (`sum`, `trace`, `norm`), the causal-matrix products | [repro] `exp1.py`/`exp2.py`/`exp10.py`: n=4000 float64 (122 MiB operands), threshold 1 byte. `a + b`: RssFile +367 MiB (a, b and c faulted in), RssAnon +0. `a @ b`: RssFile +367, RssAnon +14 (OpenBLAS buffers). `eigvals_arnoldi` n=2000: RssAnon +1. `C @ C` on a 20000² causal matrix: RssAnon +0. |
| **Tiled by the StreamingManager** (memcpy of tiles out of the same mappings into heap or temp-file tiles; the I/O is still page faults) | `matmul` (float32, float64) and `+ - * /` (float32, float64, int32, int64), only when all three are plain dense of one dtype **and** operands + result exceed the governor's RAM budget | [repro] `exp3.py`, `exp5.py`, `exp6.py` under a faked 300-400 MiB budget (method below). strace of a streamed matmul and add: `openat`/`fallocate`/`mmap(MAP_SHARED\|MAP_POPULATE)` of tile files, anonymous `mmap`s for the tile buffers, **no** `madvise`, `pread` or `msync`. |
| **Whole operand copied into heap memory** (no RAM check) | `solve`, `invert`, `det`, `cholesky`, `qr`, `lu`, `svd`/`svdvals`, `lstsq`, `eigh`/`eigvalsh`, `eig`/`eigvals` (and everything built on them: `pinv`, `cond`, `matrix_rank`) | [repro] `exp2.py` n=2000 (30 MiB operand): RssAnon peak +31 MiB for `solve`, `det`, `invert`, `cholesky`, `qr`, `svdvals`, `lstsq`; +61 `lu`; +92 `eigh`. [citation] `copy_input` (`CpuLinalg.cpp:49-53`), `CpuSolver.cpp:796,855,892`. |
| Whole operand copied, but only after a RAM check | integer matmul through float64 BLAS (3 double copies); NumPy export | [repro] int32 3000² `a @ b`: RssAnon +206 MiB (`cpu.matmul.int_via_dgemm`). It falls back to the integer kernel on the mapped pages when the copies do not fit (`CpuMatmul.cpp:515`). Export raises (export guard). |

The StreamingManager is live: it runs when the budget says so. It does not make things better.
In every case measured it was slower than the direct kernel on the same mapped pages, and it
allocated far more memory (C-1, C-2). It also fails on broadcasting (C-3). The direct path
needs no anonymous memory at all; its working set is page cache, which the OS can drop.
Recommendation: delete the StreamingManager. Before deleting, do one enforced
larger-than-RAM run (see Proposed changes 1).

### Method: a faked RAM budget
The governor reads the process's cgroup (F-124). `scripts/fakecg.sh LIMIT cmd` runs `cmd`
in a private mount namespace (`unshare -m`) where this process's v1 memory cgroup files
(`memory.limit_in_bytes`, `memory.usage_in_bytes`, `memory.stat`) are bind-mounted over
by files that say "limit LIMIT, usage 0". The governor then reports `LIMIT` as the
available RAM and `LIMIT/10` as the margin. Nothing is enforced, so a run that "exceeds the
budget" still has the machine's real RAM and cannot OOM. Nothing outside the namespace
changes. The streaming path then triggers naturally (no `_set_ram_safety_margin` hack) at
100-300 MiB operands. Caveat: the fake usage stays 0, so placements made during an operation
(the tiles) still see the whole fake budget.

## What it does
`dispatch_matmul` and the element-wise entry functions (`src/math/LinearAlgebra.cpp`)
allocate the result and call the device. `CpuDevice` (`CpuDevice.cpp:30-47`) streams when
`can_stream_*` (plain dense, one dtype, matmul float32/64, element-wise also int32/64) and
`out_of_core` (`(a.size + b.size + c.size) * elem` does not fit `can_fit_in_ram`).
Otherwise it calls the `CpuSolver` kernel.

`StreamingManager::matmul` sizes a square block from 80% of the available RAM (at least 4096,
at most `a.rows()`). It allocates three `std::vector` buffers it never uses and three
`DenseMatrix` tiles, loops i/j/k, and copies A and B tiles (twice each, see C-10). It calls
`CpuComputeWorker::matmul_tile` → `CpuSolver::gemm` (dgemm with beta = 1) and copies the C
tile back. `StreamingManager::elementwise` uses a fixed block of 4096. It allocates three
4096² tiles, a new set of exact-size tiles for every edge tile, and calls the solver's
element-wise kernel per tile.

`IOAccelerator` turns `prefetch`/`discard` into `madvise` (page-aligned since F-122). Its only
callers are `_io_prefetch`/`_io_discard`, which only the block-matrix layer uses, and
`MatrixBase::hint`. `io_observability.py` wraps traced `pc.<op>()` calls and records the
operands' facts and the engine's kernel log. `streamed` = some kernel was `streaming.*`.

## File-by-file notes

### src/compute/StreamingManager.cpp / StreamingManager.hpp
1. Purpose: tiled out-of-core matmul and element-wise ops. The header promises "prefetching,
   double-buffering logic"; there is neither. It duplicates what the direct kernels already do
   on mapped storage (OpenBLAS packs its operands into cache-sized panels itself
   [citation, OpenBLAS design]; element-wise kernels are one sequential pass).
2. Liveness: live under budget pressure only (F-026). Dead inside: `a_buf`/`b_buf`/`c_buf`
   (77-79, allocated and zero-filled, never read). The first copy of the A and B tiles
   (138-178) is overwritten by the "Re-do load strategy" copy (181-196). The `!raw_src`
   branch of `fill_tile` (274-280) is unreachable (`can_stream_elementwise` requires dense
   operands of the result dtype) and would round int64 through double. The int32/int64
   instantiations of DIVIDE are unreachable (int / int is float64). `Tag`, `Float64Tag` and
   `Float32Tag` are three tag types for one job. About 60 lines are design notes from the
   first draft ("Hack for Phase 3", "wait", "Let's assume").
3. Correctness:
   - Broadcasting operands throw `StreamingManager::elementwise dimension mismatch` (239)
     (C-3) [repro].
   - The block is computed from `a.rows()` only (65): `v @ A` gets 8×8 tiles, `A @ B` with
     a thin B gets 4096² tiles (C-2) [repro].
   - Multi-tile results are correct: n=6000 float32 under a 400 MiB budget (block 5280,
     2×2×2 tiles) gave a maximum relative error of 4e-7 against float64 NumPy, and `a + b`
     (4096 full tiles plus edges) matched exactly [repro `exp5.py`].
4. Out-of-core: it allocates about 1.6× the available RAM (C-1). Tiles are placed by the
   memory threshold, so large tiles become temp files (C-5). It sends no access hints.
5. Errors: `std::runtime_error` for dtypes that `CpuDevice` already filters. Fine.
   `invalid_argument` for shapes, which becomes the user's error message in C-3.
6. Concurrency: none. Tile loops are serial; parallelism comes from BLAS and the tile kernels.
7. Performance: 2-144× slower than the direct kernel (C-2). Every k step zero-fills the A and
   B tiles twice and copies them twice.
8. Duplication: a third dgemm call site (`CpuSolver::gemm`, used only here) next to
   `attempt_direct_path` and the `matmul_impl` fallback.
9. Docs: `Streaming Manager.md` describes the sizing correctly, but not the dead buffers, the
   rows-only block or the broadcast failure (C-11).
10. Tests: `test_streaming.py` forces the path with a 2^62 margin. Elementwise sizes ≤ 97
    never reach the full-tile branch (needs ≥ 4096). Matmul tests do get multiple tiles
    through the small aligned blocks (130 → 128; (1,200,1) → block 8). There is no
    broadcast case, no memory assertion and no size ≥ 4096.

## Findings

**C-1 (S1 critical, out-of-core crash) A streamed matmul allocates about 1.6× the available RAM
on top of its result: on this machine, a matmul that the direct path could page through would
be OOM-killed.** [repro, scaled down; full size computed]
- Where: `StreamingManager.cpp:20-41` sizes three square tiles to 80% of the governor's
  available RAM: `block = max(4096, sqrt(0.8 * avail / (3 * elem)))`. Then 77-79 allocates three
  more `std::vector<T>(block²)` that are never used. `std::vector` value-initialises them, so
  every page is written.
- Repro (`exp5.py`, budget faked to 400 MiB (360 after the margin), float32 n=6000, 137 MiB
  operands in files, threshold 1 GiB): block 5280, tile 106 MiB. `a @ b`: RssAnon peak
  +785 MiB = result 137 + three tiles 318 + three dead buffers 318. That is 2.2× the budget the
  decision was made against. Direct `a.T @ b` on the same data: RssAnon +139 (the result plus
  BLAS buffers).
  `exp3.py` (300 MiB budget, float64 n=4000): streamed +867 MiB, direct `a.T @ b` +122 (the result).
- Scenario, computed for this machine: the governor reports 11,145 MiB available. A
  square float64 matmul streams from n ≈ 20,600 (3n²·8 > available − margin). The block
  is then 19,736 and each tile is 2.9 GiB. The dead buffers take 8.7 GiB of written heap. The
  three tiles are above the 1 GiB threshold, so they become temp files of 8.7 GiB in total,
  fallocated and pre-faulted (C-5). That is 17.4 GiB in addition to the operands' pages on a
  machine with 10.9 GiB available and no swap. The direct path needs only the 10.6 GB of
  mapped operand and result pages, which the kernel can page.
- Not run at full size (it would take the machine down).
- Fix: delete the StreamingManager (Proposed changes 1). If it is kept: drop the three
  buffers; size tiles to a small fixed budget (for example 3 × 64 MiB), not 80% of free RAM;
  always put tiles in RAM.

**C-2 (S2 major, performance) Every streamed case measured is slower than the direct kernel on
the same mapped pages.** [repro]
- Measured with operand pages in the page cache (larger-than-RAM not measured, see Proposed
  changes 1):

  | Case | Streamed | Direct | Ratio |
  |---|---|---|---|
  | float64 4000² `a @ b`, 300 MiB budget | 943 ms | 437 ms (`a.T @ b`) | 2.2× |
  | float32 6000² `a @ b`, multi-tile, 400 MiB budget | 4,408 ms | 1,104 ms | 4.0× |
  | float64 (6000²) @ (6000×4), 300 MiB budget | 3,950 ms | 27 ms | **144×** |
  | `v @ A`, float64 n=6000 | 148 ms | 10 ms | 15× |
  | float64 4000² `a + b`, 300 MiB budget | 221 ms | 46 ms | 4.8× |

- Why the thin cases are so bad (`StreamingManager.cpp:65`, 34-36): the block comes from
  `a.rows()` alone, and the tiles are square and zero-padded.
  - `A @ B` with B n×4 runs four 4096³ GEMMs on mostly zero tiles: about 550 GFLOP for a
    0.3 GFLOP product.
  - A 1×n or 4×n left operand gives block 8. That is 562,500 tile iterations, each with three
    memsets, two copies and a dgemm call.
- Also: every k step zero-fills and copies the A and B tiles twice (C-10), and `CpuSolver::gemm`
  runs at the default BLAS thread count instead of the bumped one.
- Fix: delete (Proposed changes 1). If it is kept: per-dimension blocks (M, K, N), no padding,
  one copy per tile.

**C-3 (S2 major, wrong outcome) Broadcasting element-wise ops raise when they run out of core.**
[repro]
- Where: `can_stream_elementwise` (`CpuDevice.cpp:34-38`) does not check shapes.
  `StreamingManager::elementwise` requires equal shapes (`StreamingManager.cpp:237-240`).
- Repro: `exp4.py`, forced margin: `(64,64) + (1,64)`, `(64,64) * (64,1)` and
  `(1,64) - (64,64)` all fail with `ValueError: StreamingManager::elementwise dimension mismatch`.
  The same ops pass with the normal budget. Also with a natural trigger (`exp7.py`, 300 MiB
  budget): a file-backed 6000² `a + row` raises the same error.
- Scenario: centring or scaling the rows of a large file-backed matrix (`M - mean_row`) works
  in RAM and fails as soon as the data no longer fits, which is exactly when the user went
  out of core.
- Fix: delete the streaming path (the direct kernel broadcasts). Or add equal shapes to
  `can_stream_elementwise`. Regression test: a forced-margin broadcast case.

**C-4 (S2 major, out-of-core crash) Factorizations and eigensolvers copy the whole operand into
heap memory with no RAM check: an operand larger than RAM is OOM-killed instead of raising.**
[repro under the faked budget]
- Where: `copy_input` (`CpuLinalg.cpp:49-53`: `buf.assign(data, data + n*n)`). Also `svd`
  (`CpuSolver.cpp:796`), `solve` (855) and `lstsq` (892, two column-major copies). None of
  them asks the governor.
- Repro (`exp7.py`, 300 MiB budget, file-backed float64 6000², 288 MB):
  - `np.asarray(a)` raises "Export to NumPy (288000000 bytes) would not fit in free RAM".
  - `pc.determinant(a)` and `pc.solve(a, B)` both proceed: RssAnon +285 MiB and +327 MiB.
  - Their traces say `streamed: False` and nothing else.
- The docs say these need the matrix to fit in RAM (Linear Algebra Operations, "Size limits").
  Nothing enforces it, and on Linux the outcome is the OOM killer (or a stall), not an error.
- Fix, one of:
  - (a) Check `can_fit_in_ram(work bytes)` and raise `MemoryError` naming the operation and
    the size, as the export guard does.
  - (b) Better: allocate the work copy through the same placement rule as any new storage
    (RAM if it fits, else a temp file mapping). LAPACK then runs on mapped pages like every
    other kernel: slow but correct out of core, and never killed. A `MemoryMapper` scratch
    buffer is all it takes.
- Tests: the faked-budget mechanism (or a margin) plus RSS assertion.

**C-5 (S3, out-of-core) Streaming tiles are placed by the memory threshold: large tiles become
temp files that are fallocated and pre-faulted; the element-wise path creates 384 MB of unused
tiles on every call.** [repro strace]
- Where: `DenseMatrix<T> tile_a(block, block)` etc. (`StreamingManager.cpp:100-102, 247-249,
  291-293`) go through `place_in_ram` (`PersistentObject.cpp:58-60`). New files are
  `MAP_POPULATE`d when they fit (`MemoryMapper.cpp:487-488`).
- Repro: `exp6.py` with threshold 1. One streamed matmul plus one streamed add (4000²) created
  and pre-faulted 11 temp files: the two results, 3 matmul tiles, 3 unused 4096² element-wise
  tiles and 3 edge tiles. During the add, RssFile peaked at 1,146 MiB for 366 MiB of live
  data. `exp12.py`: a forced-streaming 64×64 add fallocates three 134 MB tile files.
- The result of a streamed operation (one the governor said does not fit) is itself
  `MAP_POPULATE`d, because the populate rule looks at the one object.
- In the C-1 scenario the matmul tiles are above the default threshold, so this is the default
  behaviour, not a test artefact.
- Fix: goes with C-1 (delete, or RAM tiles of a fixed small size, allocated once, edge tiles
  as views of the same buffers).

**C-6 (S3, dead decision) `attempt_direct_path`'s RAM check chooses between two identical dgemm
calls.** [citation]
- Where: `CpuMatmul.cpp:235`. When the check fails, `matmul_impl` (413-446) calls the same BLAS
  routine on the same pointers. The only differences: no gemv for N = 1 / M = 1 (slower), and no
  thread bump.
- So the "anti-nanny" rule in `Memory and Data.md` ("When the operation's operands and result
  fit in available RAM … the kernels run directly on the storage") describes a branch that
  makes no difference.
- Fix: one dgemm / sgemm call site (with the gemv case and the thread bump), no RAM check.
  `CpuSolver::gemm` goes with the StreamingManager.

**C-7 (S3) No out-of-core I/O management exists, although the docs and the header describe it.**
[repro strace + citation]
- strace of a streamed matmul and add (`exp6.py`): no `madvise`, `pread` or `msync`. The tile
  copies are plain loads from the mapping.
- No C++ operation calls `IOAccelerator`. The only callers are the block-matrix layer's
  `_io_prefetch` / `_io_discard` and the unused `MatrixBase::hint`.
- `StreamingManager.hpp:14` ("prefetching, double-buffering logic") and `Memory and Data.md`
  ("The workflow is: create (reserve space) -> prefetch -> compute -> discard") describe
  nothing that runs.
- Fix: say so in the docs. Then, measured first, a sequential read-ahead hint on file-backed
  operands in the element-wise and reduction entry functions.

**C-8 (S4) The IO trace cannot show the out-of-core facts that matter.** [repro]
- `streamed` is the only out-of-core field. A `solve` that copied 288 MB into RAM reads the
  same as one on a 4×4 matrix.
- Operators, the only calls that stream, are not traced; that is documented.
- If the StreamingManager goes, `streamed` goes with it.
- Fix: add the result's storage (`memory` / `file` / `temp`) and, from the engine, the bytes
  of any whole-operand work copy.

**C-9 (S2 on Windows, suspected; storage core, area 3.1) New files can contain stale disk
blocks instead of zeros.** [citation]
- Where: `MemoryMapper.cpp:213-219`. On create, when `EnablePrivilege(SE_MANAGE_VOLUME_NAME)`
  succeeds (an elevated administrator process), `SetFileValidData` marks the whole new file
  valid. The file then exposes whatever was on the disk, not zeros.
- Every file-backed object that relies on zero-initialised storage then reads garbage:
  - `pc.zeros` above the threshold;
  - `bit_popcount_matmul`'s transposed buffer (`CpuMatmul.cpp:163-176`, OR into fresh storage);
  - any kernel that writes only part of its result.
- It also exposes other files' deleted data in the matrix.
- `Memory and Data.md` advertises it ("reserves file space without zero-filling it").
- Not run (no Windows).
- Fix: drop `SetFileValidData`, or use it only under `UninitializedStorage` (where every byte is
  written before it is read).

**C-10 (S4) Dead and duplicated code in the streaming path.** [citation]
- `StreamingManager.cpp`:
  - the three unused buffers (77-79, also C-1);
  - the first A/B tile copy (138-178), overwritten by 181-196;
  - the unreachable `get_element_as_double` branch (274-280) and DIVIDE for integers;
