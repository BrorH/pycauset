## What it does
`promotion::resolve(op, a, b)` gives the result dtype of a binary matrix or vector operation
from the two dtypes: complex beats float beats int beats bit; within floats, the smaller
precision wins (under-promotion); a cross-kind result must hold the integer operand
(F-034); int ÷ int gives float32 or float64; signed ⊕ uint64 raises (F-035b); bit ⊕ bit
counts in int32, except bit * bit (bool). `structure::resolve_result_structure` gives the
result structure of `+ - *` from the operands' classes and orientation: transpose pairs
(`A ± A.T`), diagonal, symmetric, antisymmetric, upper triangular, and packed Hermitian
pairs. Otherwise the result is dense.
`DTypeDispatch.hpp` is the catalogue (F-087): `offered<S, T>`, `ClassOf<S, T>`, the three
builders (`make_matrix`, `open_matrix`, `adopt_matrix`), `visit_matrix` / `visit_vector`,
and the dtype and structure names. `ObjectFactory` is a static facade: `create_matrix` forwards
to `make_matrix` and `clone_matrix` to `adopt_matrix`. The vector functions are still hand
switches. `MatrixTraits<T>` maps the element type to its `DataType` and a file-name prefix.

On the Python side, `_internal/dtypes.normalize_dtype` turns user dtype tokens into names. The
list-input constructors (`matrix_api.Matrix`, `factories.vector_factory`) infer a dtype from
Python values.

How it compares with NumPy, measured [repro]:
- `pairs.py`: every matrix ⊕ matrix pair gets exactly the resolver's dtype (1,125 cells,
  0 differences). So the kernels honour the resolver.
- Against NumPy, 120 of the 1,125 cells differ.
  - Documented: float under-promotion, bit counting, F-035b, and int ÷ int giving float32 (24
    pairs; DType System §2 rule 5).
  - Not documented: the complex under-promotion (10 pairs per op, C-7).
- The scalar path is a second resolver with other rules (C-3, C-4).

## Findings

**C-1 (S1 critical, silent wrong values) Element-wise structure rules ignore broadcasting: a 1×1
operand turns `D + c` into a diagonal result without the off-diagonal values.** [repro]
- Where: `src/core/StructureResolver.cpp:92` checks that each operand is square, not that the
  shapes are equal. A 1×1 operand is square and broadcasts. The rules at 101, 106-108 and 111-112
  then keep the structure of the n×n operand.
- Repro (`/tmp/claude-0/review33/bcast.py`):
  ```
  Diagonal(3) + Diagonal(1)   -> DiagonalMatrix   [[6,0,0],[0,7,0],[0,0,8]]   NumPy [[6,5,5],[5,7,5],[5,5,8]]
  Diagonal(3) + Identity(1)   -> DiagonalMatrix   (same pattern)
  Triangular(3) + Diagonal(1) -> TriangularMatrix lower part 0                NumPy 5
  Hermitian(3) + Hermitian(1) -> RuntimeError "Unsupported result type in binary_op_impl"
  Identity(3) + Identity(1)   -> ValueError "add: identity operands must have identical shapes"
  ```
  The last one comes from `LinearAlgebra.cpp:83-85`, where NumPy broadcasts.
- Scenario: `D + pc.diagonal([c])`, or any structured operand combined with a 1×1 result of an
  earlier step (e.g. a 1×1 `pc.matrix` from a reduction kept as a matrix).
- Fix:
  - In `resolve_result_structure`, return DENSE unless both operands have the result's shape
    (`a.rows() == b.rows() && a.cols() == b.cols()`), before any rule.
  - In `identity_pair`, return `nullptr` (the general path) instead of throwing on unequal
    shapes; the general path broadcasts.
- Test: every structure ⊕ each 1×1 structure, against NumPy (an atlas pair dimension
  "broadcast").

**C-2 (S1 critical, silent wrong values) `I @ X` rounds int64 / uint64 values through float64.**
[repro]
- Where: `dispatch_matmul`'s identity rule (`src/math/LinearAlgebra.cpp:700-708`) multiplies X
  by `ScalarArg::from_double(1.0)`. That is a weak Python float. `scalar_result_dtype` promotes
  an integer matrix times a Python float to float64, and the result is then cast back to r.
- Repro (`/tmp/claude-0/review33/ident.py`):
  ```
  I(int64) @ X, X[0,0] = 2**60 + 1   -> int64, value off by -1    (also X @ I, I @ v, v @ I)
  I(uint64) @ U, U[0,0] = 2**64 - 1  -> uint64, value 0
  dense eye(int64) @ X               -> exact
  ```
- This is the F-036 class again. F-036 routed the shortcut through `scalar_op` so that it would
  follow the resolver, but the argument type makes scalar_op pick another dtype. Root cause: C-3
  (two resolvers).
- Fix: the identity rule must not go through a dtype decision of its own.
  - Pass the factor as an exact integer `ScalarArg` (or as a strong scalar of dtype r) when it
    is real and integral.
  - Better: compute `cast_to(other, r)` and scale in r through the view-factor path (exact
    integer factors, F-042).
- Regression test: `test_F-new_identity_matmul_int64_exact` (int64, uint64, both sides,
  matvec).

**C-3 (S2 major) Two promotion tables disagree: matrix ⊕ scalar does not follow the documented
rules.** [repro]
- Where: `promotion::resolve` (`src/core/PromotionResolver.cpp`) for matrix ⊕ matrix versus
  `scalar_result_dtype` + `promote_ints` (`src/math/ScalarOps.cpp:114-189`) for matrix ⊕ scalar.
- Repro (`/tmp/claude-0/review33/incons.py`):

  | expression | PyCauset | the other form in PyCauset |
  |---|---|---|
  | `float16 M + np.float32(1)` | float32 (widens) | `float16 M + float32 M` → float16 (under-promotes) |
  | `float64 M * np.float16(1)` | float64 | `float64 M * float16 M` → float16 |
  | `int8 M + np.uint64(1)` | float64 | `int8 M + uint64 M` → ValueError (F-035b decision) |
  | `int8 M / 1`, `int8 M / np.int8(1)` | float64 | `int8 M / int8 M` → float32 |
  | `bool M / True` | float64 | `bool M / bool M` → float32 |

- The scalar path follows NumPy (NEP 50). The matrix path follows DType System. F-035b
  deliberately chose to raise rather than silently round through float64; the scalar path does
  what that decision rejected.
- Architecture.md and Adding Operations §1 say the result dtype "comes from
  `promotion::resolve`"; for scalar ops it does not.
- Decide one rule per question (maintainer):
  1. Does under-promotion apply to strong NumPy scalars?
  2. Does int ⊕ uint64 raise for scalars too?
  3. int ÷ int: float32 or NumPy's float64?
- Then implement the scalar case inside `promotion::resolve`: a `resolve_scalar(op, dtype,
  ScalarArg)` next to `resolve`, sharing the kind tables. Delete `ScalarOps.cpp`'s copies
  (`promote_ints`, `float_for_int`, `max_float`, the kind predicates).
- Test: one table-driven test that compares both forms for every dtype and scalar kind, and
  both against NumPy with the documented exceptions listed.

**C-4 (S2 major) `np.float64` and `np.complex128` scalars are treated as weak Python scalars.**
[repro]
- Where: `src/bindings/scalar_args.hpp:63-65`. `PyFloat_Check` / `PyComplex_Check` come before
